# T6.3 — Live region, announcements, instructions wiring

**Phase** P6 — Overlay, auto-scroll, accessibility · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Make a drag audible to a screen reader: a visually-hidden live region that announces
pickup, target changes, drop, and cancel, plus the hidden instructions element that
`aria-describedby` on every handle points at. All texts overridable, none of them
hard-coded in English inside a component.

## Test first

Red tests before implementation:

- Announcement text appears in the live region on start / over-change / drop / cancel —
  asserted through the rendered DOM, driving a real drag, not by calling the announcer.
- **Over-change only announces on change** — moving within the same droppable must not
  re-announce, or the region becomes noise.
- Custom texts from `DndProvider`'s `accessibility` prop override every default
  (accessibility invariant 2).
- **Announcements branch on `DragCancelReason`** ([T2.1](T2.1-public-types.md)), but only one
  member needs its own text:
  - `'escape'`, `'blur'`, `'pointer-cancelled'` → the ordinary "movement cancelled" text. From
    the user's point of view the drag simply stopped, and three near-identical strings would be
    noise.
  - `'item-removed'` → **its own text**, because "movement cancelled" is a lie there: the user
    cancelled nothing, and a screen-reader user has no other way to learn what happened. It
    must say the item was removed and that the dragged item returned to its original position
    ([`ANALYSIS.md`](../ANALYSIS.md) § A6).
  All of them overridable via the `accessibility` prop, like every other text.
- The live region is visually hidden but *not* `display: none` / `hidden` — that would
  make it invisible to assistive tech too. Assert the actual style.
- The instructions element exists, has a stable id, and every draggable's
  `aria-describedby` resolves to it (accessibility invariant 3).
- Announcements fire identically for pointer and keyboard drags.

## Acceptance criteria

- `src/internal/live-region.tsx` — visually-hidden container with the right `aria-live` /
  `role` semantics.
- `src/internal/announcements.ts` — the default text builders, pure and separately testable.
- Both wired in `DndProvider` ([T4.1](T4.1-dnd-provider.md)); ids generated per provider so
  two providers don't collide.
- Internal only — not in the `exports` map. The `accessibility` prop is the public surface.
- `'use client'` on the live region; `announcements.ts` stays pure and directive-free.

## Where it stands

`src/internal/announcements.ts`, the announcer half of `src/internal/live-region.tsx`, and
both test files on disk (2026-08-08); 20 tests green, `bun run verify` clean. The
`DragInstructions` half of `live-region.tsx` was created at

before this task's turn came.

### The region subscribes itself rather than being handed a message

`DndLiveRegion` takes the store and calls `store.addMonitor` in its own effect, so **it** is
the only thing that re-renders per announcement. Passing the message down as a prop would have
put a `useState` in `DndProvider` and re-rendered the whole subtree on every target change —
undoing perf invariant 4 through the accessibility layer, which is exactly the kind of
regression nobody notices.

"Over-change only announces on change" needs no logic here at all: the store already fires
`onDragOver` only on a change ([T3.1](T3.1-store.md)). Asserted anyway, with ten moves inside
one target leaving the text untouched.

`role="status"` + `aria-live="assertive"` + `aria-atomic`: a drag is a direct response to the
user's own action, so it should interrupt rather than queue behind whatever else is being read.

### The cancel texts, and the one that is not shared

`'escape'`, `'blur'`, and `'pointer-cancelled'` share a single "Movement cancelled" string —
from the user's point of view the drag simply stopped, and three near-identical strings would
be noise. `'item-removed'` gets its own: *"The list changed while you were dragging. X returned
to its starting position."* Its test asserts the text does **not** contain "cancelled", because
that word would be a lie — the user cancelled nothing, and a screen-reader user has no other
way to learn what happened.

All four are asserted to say the item went back to where it started.

### Overrides merge per key rather than replacing the set

`{ ...DEFAULT_ANNOUNCEMENTS, ...accessibility.announcements }`, so a consumer overriding two
texts keeps the other two. Tested by overriding start and end, then asserting the *default*
over-text still appears in the middle of the same drag.

### Pointer and keyboard say the same things

Asserted by comparing the exact drop announcement from a pointer drag against the one from an
equivalent keyboard drag. It holds because announcements are built from the event payload,
which carries no trace of which sensor produced it.

That test also found a testing trap worth recording: two `render` calls in one test both
resolve `getByRole('status')` against the whole document body, so the scene helper scopes its
queries to `within(view.container)`.
