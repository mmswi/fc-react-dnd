# T11.12 — A root entry, reversing "no root entry, on purpose"

**Phase** P11 — Defects found after v0.1 · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

Asked for by the user 2026-08-12, looking at the Quickstart's import block: *"thinking at how
customers use a library, we need to offer the exports from a single place, like from
`fc-react-dnd`… meaning no more imports like this"* — four lines from four subpaths to build one
sortable list.

**This reverses a locked decision**, and the reversal is the user's call, made with the trade-offs
below on the table. What it replaced: `CLAUDE.md` ground rule 4 ("No barrel files. Anywhere.
Including `src/index.ts`"), a README section titled *There is no root entry, on purpose*, and a
`CHANGELOG.md` 0.1.0 constraint reading "No root entry point".

## Why the original rule was weaker than it looked

The stated reason was tree-shaking: *"a barrel pulls the whole library into your module graph the
moment you import one thing from it."* That is true of a CJS barrel, or an ESM one whose modules
have side effects. **This package is neither** — ESM-only, `"sideEffects": false`, per-file `tsc`
output with no bundler in the chain. Any bundler that does cross-module DCE drops what you never
import. The shipped-bytes argument does not survive contact with this package's own manifest.

## What survives, measured — and the claim that did not

The first version of this task, the README and `index.ts` all said importing the pure maths through
the root "drags the client modules in" and would hurt a **server component**. The user asked why.
Measuring it showed that was **overstated**, so all three were corrected. Both numbers below are
from the built `dist/`, not from reasoning:

| | modules resolved | `react`/`react-dom` |
| --- | --- | --- |
| `import { applyTreeDrop } from 'fc-react-dnd/tree'` | **1** | none |
| `import { applyTreeDrop } from 'fc-react-dnd'` | **86** | 18 |

Measured with a `node:module` `resolve` hook counting resolutions, run from inside the package so
self-referencing applies.

**Under a bundler the cost is zero.** A Vite/Rollup lib build aliased at `dist/`, importing only
`applyTreeDrop` from the root, emits **4,144 bytes** containing `applyTreeDrop` and `flattenTree` —
and zero occurrences of `DndProvider`, `createPortal`, `useSyncExternalStore`, `pointerSensor` or
`SortableList`. `sideEffects: false` plus ESM does exactly what it promises.

So the real rule is **not** about server components — Next bundles those too, and DCE applies.

**And then the corrected version was cut from the docs as well**, on the user's second push: *"who
doesn't use a bundler? you are making things confusing."* Right again. The remaining difference is
**8.0 ms vs 0.8 ms, once, only unbundled** — timed over `dist/`. Every consumer of a React DnD
library goes through Vite, Next, webpack or Parcel, so the population that ever pays it is roughly
a Node script or a test, and 8 ms is not something to warn them about.

The lesson worth keeping: a measured difference is not automatically a documented one. `86 vs 1`
sounds alarming and is 8 ms; leading a README's *Importing* section with it made the simple thing
look complicated, which is a worse outcome than the cost it was warning about. The numbers live
here; the README says "both work, use whichever reads better".

## Why this was safe to do now, and would not have been last week

A barrel can only re-export a **collision-free** surface. Until
[T11.9](T11.9-tree-drop-indicator-name-collision.md) landed hours earlier, `TreeDropIndicator` named
two different public exports — the anchor type in `tree.ts` and the component in
`tree-drop-indicator.tsx` — so `src/index.ts` would not have compiled. The sweep confirming zero
duplicate public names is the precondition, not a formality.

## Shape

- `src/index.ts`, re-exporting **by name**, never `export *`. It reads as a manifest of the public
  surface, and a new export must be added deliberately rather than appearing by wildcard.
- Every one of the 15 subpaths stays published. This is **additive** — no consumer import breaks.
- No `'use client'` on the barrel itself; the modules it re-exports carry their own.

## The red test

`src/public-api.test.ts` gained a `'.'` entry pinning all 24 root value exports, and the import of
`./index.js` before the file existed. The suite failed to load
(`Failed to resolve import "./index.js"`), then the pin failed against `package.json` until `"."`
was added to the export map. The pin is what keeps the barrel honest: add an export to a module,
forget the barrel, and the suite fails.

Verified beyond the suite: `attw` reports the root `🟢 (ESM)` / `🟢 bundler`, and
`node -e "import('fc-react-dnd')"` loads it with all 24 value exports.

## Acceptance criteria

- `import { … } from 'fc-react-dnd'` resolves for every public value and type.
- Every existing subpath still resolves; nothing about `internal/` becomes reachable.
- The root's exports are pinned by name in `public-api.test.ts`.
- `CLAUDE.md` ground rule 4 and the module map state the new rule; the README's *Importing* section
  replaces *There is no root entry, on purpose* and every example imports from the root.
- `bun run verify` green.
