# T4.5 — React API component tests

**Phase** P4 — React API · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

The cross-cutting tests that no single P4 hook owns: the whole registration lifecycle
under StrictMode, render-granularity across a realistic tree of draggables and droppables,
and provider callbacks firing in the right order with the right payloads.

## Test first

This task *is* tests. Each hook's own red tests were written in T4.1–T4.4; here the
subject is their interaction — the failure modes that only appear once several
components share one provider.

## Acceptance criteria

- **StrictMode lifecycle:** a tree of draggables and droppables mounts, drags, and
  unmounts inside `<StrictMode>` with no double registration, no double subscription, no
  leaked listener (perf invariant 8). Assert on the store's registry sizes, not on the
  absence of console warnings.
- **Granularity, realistically:** with N draggables and N droppables mounted, one full
  drag crossing one boundary re-renders a bounded, asserted number of components —
  written as an exact expected count so a regression fails loudly instead of drifting.
- **Callback order and payloads:** start → move/over → end fires in order, each with the
  documented payload (active, over, translate), and cancel replaces end when Escape is
  used.
- Tests drive the public API and real DOM events only — never sensor or store internals.
- Uses `mockElementRect` from [T1.5](T1.5-test-harness.md) for positioning.

## Where it stands

`src/react-api.test.tsx` on disk (2026-08-08); 10 tests green, `bun run verify` clean.
Sequenced after [T5.1](T5.1-pointer-sensor.md) as this file suggested, so every test drives
real `pointerdown` / `pointermove` / `pointerup` / `keydown` through the public API.

Ten rows, each one element registered as **both** a draggable and a droppable — which is what
a sortable row is, and the shape where cross-hook problems actually appear.

### The counts, and the method

**Committed renders**, counted from a `useEffect` with no dependency array. That is
unambiguous under both of React's bailout paths, including the late one where the body runs
and its output is discarded — so these numbers mean the same thing as
[T9.6](T9.6-chrome-qa-and-profiler.md)'s Profiler numbers will.

- Crossing one row boundary commits **exactly rows 0 and 2** — the one that lost `isOver` and
  the one that gained it. The other eight have no changed slice and do not commit.
- Twelve pointermoves inside one row commit **nothing at all**.
- Drag start commits **only the dragged row**.

### Registry assertions read `measuredRects.size`, not a debug accessor

"No double registration, no leftovers" needs an observable, and adding a test-only registry
accessor to the store would be production API existing for a test. `measuredRects` holds one
entry per registered droppable, so its size is the honest one — ten rows, ten entries, checked
inside `<StrictMode>`. Unmounting then makes `beginDrag` return `null` for every id.

Worth stating for whoever reads the criteria: with the registries keyed by id in a `Map`, a
literal *double* registration is unrepresentable — a second register overwrites. What these
tests actually guard is the failure that **is** representable: a leaked or missing entry after
StrictMode's mount → unmount → mount.

### Two corrections made while writing this file

- A test named "reports no over at all when the drag lands off every target" was asserting a
  *cancel* instead. `closestCenter` has no range limit by design, so with any droppable
  mounted there is always an `over`; the null case needs a subtree with none. Rewritten to do
  exactly that and assert `over === null` on the drop.
- Biome's `noArrayIndexKey` rejected `key={index}` — and it was right to in this repo
  specifically, since keying lists by id rather than index is a documented consumer contract
  ([`ANALYSIS.md`](../ANALYSIS.md) § A6 case 5). The test fixture now keys by row id.
