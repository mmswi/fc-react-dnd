# T7.6 — The hooks return a ready-to-spread `style`

## Goal

`useDraggable`, `useSortable` and `useTreeDrop`'s row props each return `style: DragNodeStyle` —
`transform`, `transition` and `touch-action` in one object, correct by default.

API addition across three hooks, so its own task per the public-API policy. Opened by the user
(2026-08-08), quoting the block every consumer was writing by hand:

> these styles should be in the library already and added on the elements by default, but with
> the possibility to customize. without them, the dragging looks wrong

## The test that opens it

`src/use-sortable.test.tsx` — the one that names the failure nobody sees on a desktop:

```ts
it('carries touch-action even before a drag, so a spread cannot lose it', () => {
  const list = renderList()

  expect(list.styleOf('a')).toEqual({ touchAction: 'none' })
})
```

## Acceptance criteria

- `style.touchAction` is always `'none'`, drag or no drag, on all three hooks.
- A displaced row gets `transform` **and** the settle `transition`; the dragged row gets
  `transform` only; the commit that ends a drag gets neither.
- A row that has not moved has **no** `transform` key at all — not an identity transform.
- `transition` on `UseSortableOptions` overrides the easing; `null` disables it.
- `translate` and `transition` stay on the result for consumers driving their own animation.
- All three playground pages consume `style` and hand-assemble nothing.
- `bun run verify` green; README examples still compile.

## Where it stands

Done. 485 tests, `verify` green, and confirmed in Chrome: `touch-action: none` on every row, a
transform on the dragged row, `transition-property: transform` on a displaced one, nothing at
rest, and the drop landing where aimed.

### Why the library owns this now

Three separate things had to be assembled by hand, and each fails differently:

| Forget | Symptom |
| --- | --- |
| `transform` | nothing moves |
| `transition` | a dropped row glides in from its old offset instead of landing |
| `...handleProps.style` | `touch-action` lost — **breaks touch dragging and nothing else** |

The third is the one that justifies the change. `{...handleProps} style={mine}` overwrites the
handle's own style object, and the consequence is invisible on every desktop the author tests
on. All three playground pages were merging `handleProps.style` by hand, which is the honest
evidence: the demo written *by* the library author, three times, remembered a step a consumer
will not.

### Deliberately not included

**`opacity`.** Ghosting the source row is taste, not mechanism — a list whose motion is carried
by a `DragOverlay` wants the opposite. It stays a one-liner after the spread, and the README
says so rather than the library assuming.

### No transform at rest, on purpose

`buildNodeStyle` omits `transform` entirely when the translate is zero rather than emitting
`translate3d(0px, 0px, 0)`. An identity transform still promotes an element to its own
compositing layer, so the alternative costs N layers across a list to say nothing happened.

### `useDraggable` gets no transition, and `useTreeDrop` no transform

Both are the type being honest about what the hook can know. A plain draggable has no displaced
neighbours to settle, and easing the element under the pointer would make it lag the hand. Tree
rows are measure-only and do not translate at all while tree mode is indicator-only — but they
still need `touch-action`, so their `style` is a single frozen object shared by every row of
every tree.
