# T8.3 — Dragging left lifts a row out of its parent

## Goal

Make un-nesting reachable from anywhere in a group. Pulling the pointer left by one indent step
makes the dragged row a sibling of its parent; another step makes it a sibling of its
grandparent; further steps stop at the root.

Opened by the user after hands-on testing:

> it's complicated to take a child out of its parent. if I drag left, it should get out of the
> parent to the level it is dragged on (brother with the parent, or even brother with the
> parent's parent)

The reasoning, including why the old floor existed and why lowering it is safe, is
[§ A10](../ANALYSIS.md).

## The test that opens it

`src/tree.test.ts`, in the gap between `guide` and its own child `usage` — a gap where every
bounding row sits at depth 1 or deeper, so the old floor admitted no way out:

```ts
it('makes the row a sibling of its parent', () => {
  const projection = project({ activeId: 'install', pointerY: gapInsideGuide, depthSteps: -1 })

  expect(projection).toMatchObject({ depth: 1, parentId: 'docs', afterId: 'guide' })
})
```

## Acceptance criteria

- One step left makes the row a sibling of its parent; two steps, a sibling of its grandparent.
- Any further leftward travel settles at the root rather than overshooting or returning `null`.
- A row dragged in with **no** horizontal movement still joins the group it was aimed at — the
  regression this feature can most easily cause.
- `ArrowLeft` steps out of one enclosing group at a time and reaches the root, so the keyboard
  and the pointer keep sharing one projection.
- No adoption: rows below the drop keep the parent they had, asserted through `applyTreeDrop`
  rather than through the projection alone.
- `bun run verify` green.

## Files touched

- `src/tree.ts` — the floor becomes root-deep for a leftward pull, `next.depth` otherwise.
- `src/tree.test.ts` — four new cases; two existing ones rewritten (see below).
- `src/use-tree-drop.test.tsx` — the keyboard depth-range expectation.
- `playground/src/tree-page.tsx` — the indicator anchor.
- `.claude/ANALYSIS.md` — § A10.

## Where it stands

Done. 462 tests green, `verify` green.

**The change is one line of rule and a great deal of reasoning.** `lowestDepth` was
`next?.depth ?? 0`; it is now `0` when `Math.round(offsetX / indentPx) < 0` and unchanged
otherwise. Everything downstream already worked: `ancestorOrSelfAtDepth(prev, depth)` walks up
to the ancestor at the requested depth and lands after it, so a shallower depth already had a
legal position waiting further down the list.

The asymmetry is the whole design. An unconditional floor of `0` is the obvious wrong fix — a
row arriving from the root requests depth 0, so it would land *beside* every group it was
dropped into instead of inside it. That case is now a test.

### Two existing tests were rewritten, and one of them was wrong on its own terms

- *"cannot go shallower than the row below the gap"* asserted the old rule directly. Rewritten
  to assert what still holds: the floor lifts a row that expressed no horizontal intent.
- *"does not let a far-left drag adopt the subtree that follows it"* kept its name and lost its
  premise. Its comment feared that a far-left drag would become "install's parent's sibling and
  swallow it" — but `applyTreeDrop` splices the active node into the target parent's children
  and re-parents nothing else, so adoption was never expressible at any floor. It now asserts
  the real invariant through the applied tree, where an adoption would actually show up.

Both are cases of a test encoding *the rule as implemented* rather than the behaviour the rule
was for. They passed for as long as the rule stood and said nothing about whether it was right.

### The indicator was pointing at the wrong row, which read as the same bug

`afterId` names the row the drop follows **among its siblings**, not the row it follows **on
screen**. Lifting a document to the root lands it after that ancestor's entire visible subtree,
and the playground drew the line immediately below the ancestor's own row — several rows above
where the document would appear. So even the un-nests that already worked (from the last gap of
a group) looked like they had gone somewhere else entirely.

Fixed in `tree-page.tsx` by advancing the anchor to the last row of its subtree — in a flattened
tree, the rows that follow it while staying deeper.

**Open API question, deliberately not decided here:** every consumer drawing an indicator needs
that same walk. That is an argument for the library returning the visual anchor alongside the
sibling one, and it is an API addition, so it needs its own task rather than a quiet addition to
this one.

### Method note

The suite had 59 tree tests and all of them passed while this was broken, because they check the
projection against the rule as written. A rule can be implemented perfectly and still be the
wrong rule. Both halves of this task came from a person dragging a real tree.
