# T2.2 — `src/internal/geometry.ts`

**Phase** P2 — Core primitives · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Pure rect math, no DOM and no React, so it can be tested exhaustively in milliseconds.
Everything expensive in this library reduces to arithmetic on cached rects; this is that
arithmetic.

## Test first

Red tests before implementation, table-driven on hand-computed rects:

- Centre of a rect; translating a rect by a `Translate`.
- Distance between centres — including the degenerate zero-distance case.
- `findDroppableInDirection` (keyboard targeting): from a start rect and a direction,
  pick the nearest candidate **in that direction**. Cases that must be red first:
  candidates strictly behind the direction are excluded; a candidate directly ahead beats
  a closer one off-axis (axis-weighted score); no candidate ahead returns nothing rather
  than the nearest anywhere; ties resolve deterministically.

## Acceptance criteria

- Pure functions only — no `document`, no `window`, no React import, no `'use client'`.
- `findDroppableInDirection` filters by direction first, then scores with the movement
  axis weighted more heavily than the cross axis, so keyboard navigation feels like
  "next item over" rather than "nearest thing on screen".
- Deterministic tie-breaking (stable by registration order), asserted by a test.
- Named constants for any weighting factor — no bare literals in the scoring, per repo
  conventions.
- Feeds both [T5.2](T5.2-keyboard-sensor.md) and [T2.3](T2.3-collision-closest-center.md)
  without either importing DOM code.

### The function is named `findNearestRectInDirection`, not `findDroppableInDirection`

Two reasons, both about the name telling the truth:

- Its candidates are **not all droppables**. [T5.2](T5.2-keyboard-sensor.md) requires keyboard
  targeting to step through measure-only tree rows, which are registered rects that collision
  never sees (§ A7 D3). A function called `findDroppable…` would be lying to every reader of
  the keyboard sensor.
- `findTargetInDirection` — the obvious alternative — is already the name of the `DragSession`
  method that wraps this one ([T2.1](T2.1-public-types.md)). One name, one thing, package-wide:
  the session method is the drag-aware query, this is the pure rect math underneath it.

### The scoring criterion above is worded backwards; the tests are the spec

The criteria say "the movement axis weighted more heavily than the cross axis", but the test
criterion in the same file says "a candidate directly ahead beats a closer one off-axis" —
and those two cannot both hold. Worked example: from centre (50, 20) going down, a candidate
straight down at 100px versus one 60px down and 80px sideways. Weighting the *movement* axis
harder picks the diagonal. Only penalising the **cross** axis picks the aligned one, which is
what makes ArrowDown feel like "the next item down" rather than "the nearest thing lower".

Implemented as `alongDirection + offAxisDistance * CROSS_AXIS_PENALTY` with the penalty at 2.
The constant is module-private and deliberately **not** asserted by value — a test that pins
the number is tautological and breaks on any retune. The behaviour test above pins it instead.

Direction filtering happens before scoring (`alongDirection > 0`, strictly), so a candidate
behind the movement can never win however close it is, and a candidate sharing the start
centre is excluded rather than counted as distance zero. Ties keep the first candidate in
array order — registration order — which the test asserts in both directions.
