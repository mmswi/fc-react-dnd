# T11.1 — One indent width, not two

**Phase** P11 — Defects found after v0.1 · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

`indentPx` describes one physical quantity — how wide one level of nesting is — and the library
stores it twice, in two independently-configurable options with two separately-defaulted
constants:

```
keyboard-sensor.ts:25   DEFAULT_INDENT_PX = 24        ← keyboardSensor({ indentPx })
tree.ts:174             DEFAULT_TREE_INDENT_PX = 24   ← useTreeDrop({ indentPx })
```

The keyboard sensor emits a **pixel** translate of `±indentPx` per ArrowLeft/ArrowRight
(`keyboard-sensor.ts:92-98`). The tree projection then recovers a step count by dividing
`translate.x` by *its own* `indentPx` (`tree.ts:320`):

```
depthSteps = round(keyboardIndentPx / treeIndentPx)
```

Both default to 24, so `round(1) = 1` and the keyboard behaves. Change one and the arrow keys
silently stop meaning "one level".

Found while answering a question about `indentPx` during the 2026-08-08 code review, not by a
test. Two constants for one quantity is exactly what `CLAUDE.md`'s single-source-of-truth rule
exists to prevent.

## The bug, reproduced

Against `dist/`, one ArrowRight press (sensor at its default 24, so `translate.x = +24`),
dragging `onboarding` (depth 1) into the gap below `oncall` — a gap that legally admits depths
0 through 3, so the clamp is not masking anything:

| `useTreeDrop({ indentPx })` | `depthSteps` | resulting projection |
| --- | --- | --- |
| `24` (matches the sensor) | 1 | `depth 2, parentId engineering, index 2` — correct |
| `16` | 2 | `depth 3, parentId oncall, index 0` — **two levels, different parent** |
| `64` | 0 | `depth 1, parentId handbook, index 2` — **the keypress does nothing** |

The `16` case is the dangerous one: `round(24/16)` is `round(1.5)` = 2, so a single keypress
skips a level *and* re-parents into a node the user never aimed at. It is not a rounding wobble
that lands somewhere adjacent — the drop commits to a different parent.

A consumer hits this the moment they match the library to a design system whose indent is not
24px, which is the ordinary case, and the pointer path keeps working the whole time — only the
keyboard breaks. That makes it an accessibility defect, not just a config wart.

## The test that opens it

`src/use-tree-drop.test.tsx` — the keyboard path with a non-default indent, which no existing
test covers (every current keyboard test runs both sides at 24, where the bug is invisible):

```ts
it('steps exactly one depth level per ArrowRight, whatever indentPx is', () => {
  renderTree({ indentPx: 16 })            // sensor left at its own default of 24

  pickUp('onboarding')                    // starts at depth 1
  arrowRight()

  expect(latestProjection()).toMatchObject({ depth: 2, parentId: 'engineering' })
  // currently: { depth: 3, parentId: 'oncall' }
})
```

A second case pins the other direction — `indentPx: 64`, where the keypress is currently a
no-op and the assertion is that depth still advances by one.

## The decision this needs first

The fix is an API decision and must not be made inside this task file. Add an `ANALYSIS.md`
entry (next free number, § A11) weighing at least:

- **Sensor stops owning an indent.** `keyboardSensor` emits a step of one *unit* and the tree
  scales it. Cleanest single source, but the sensor currently emits pixels by deliberate design
  — it "knows nothing about trees" (T5.2), and a unit-shaped translate leaks tree semantics into
  a generic sensor. It also changes what a horizontal step means for the backlogged horizontal
  `SortableList` case.
- **One shared constant, two options.** Both defaults derive from a single exported
  `DEFAULT_INDENT_PX`, and the docs state that overriding one requires overriding the other.
  Kills the duplicated literal; leaves the coupling live and undetectable.
- **`useTreeDrop` feeds the sensor.** Correct by construction, but sensors are configured on
  `DndProvider` while `indentPx` is per-tree, so it needs a channel that does not exist.
- **DEV-mode warning on disagreement.** Cheap, catches it at the moment of the mistake, and
  composes with any of the above rather than replacing one.

Whichever wins, exporting or renaming an option is a public API change and is governed by
`CLAUDE.md` § "Public API policy".

## Acceptance criteria

- One ArrowLeft/ArrowRight press changes the projected depth by exactly one level, for any
  `indentPx`, with the keyboard sensor and `useTreeDrop` configured independently.
- The `indentPx: 16` and `indentPx: 64` cases above both hold; neither re-parents into an
  unaimed node nor silently no-ops.
- Exactly one constant in `src/` defines the default indent width; a grep for a second
  `INDENT_PX` default returns nothing.
- The pointer path is unchanged — the existing tree projection tests stay green untouched,
  since `offsetX` from a pointer is a real pixel distance and always was.
- The chosen design is recorded in `ANALYSIS.md` § A11 with the rejected options and why.
- If the resolution changes a public option or export, the README and the `use-tree-drop` /
  `keyboard-sensor` doc comments say what a consumer must now set.
- `bun run verify` green.

## Where it stands

Done (2026-08-09). 492 tests, `verify` green. Design recorded in
[`ANALYSIS.md`](../ANALYSIS.md) § A11.

**The tree publishes its indent to the store; the keyboard sensor asks the session for it.**
`store.setCrossAxisStepPx(px)` is a registration (no notify, no render), `useTreeDrop` calls it
from an effect with its resolved `indentPx`, and `DragSession.crossAxisStepPx()` is how the
sensor reads it. `translate.x` stays a real pixel distance, so the overlay, the projection
arithmetic and the whole pointer path are untouched — only the *source* of the sensor's step
moved.

`keyboard-sensor.ts`'s `DEFAULT_INDENT_PX` is deleted. `KeyboardSensorOptions.indentPx` survives
as an explicit fallback with **no default**, because the tree maths is public and someone
driving `projectTreeDrop` without `useTreeDrop` needs a lever; a published value wins over it.
With neither, a horizontal step is a no-op, which is honest — nothing in that drag reads a
horizontal offset.

`grep -rn "INDENT_PX = " src/` now returns exactly one line: `tree.ts`'s
`DEFAULT_TREE_INDENT_PX`.

### On the tests

Four cases at the sensor seam (`keyboard-sensor.test.tsx`): session value used, session beats
the option, option used when nothing published, no-op when neither exists. Three at the
composition (`use-tree-drop.test.tsx`), whose harness now lets the two indents disagree —
`renderTree({ treeIndentPx })` with the sensor given no option at all.

**Two of the composition tests were vacuous when first written and had to be rebuilt**, which is
worth recording because it is the same trap this defect came from. Asserting "one press moves
one level" from *rest* proves nothing at a gap whose floor is depth 1: the floor absorbs the
first step whatever the arithmetic did. And at `indentPx: 16` the gap's *ceiling* of 3 hides the
1.5-level overshoot until the third press. The discriminating assertions turned out to be
cross-indent agreement (the same press count must land on the same depth for 8/16/24/64) and
press-to-press deltas measured away from both bounds. Confirmed by removing the fix: all three
fail.

Opened 2026-08-08 during the code-review pass that preceded the blog post rewrite.

The defect is **verified, not theorised** — the table above is real output from `dist/`, produced
by calling `flattenTree` + `projectTreeDrop` directly with the keyboard sensor's own default
step as `offsetX`. The scratch script was deleted after reading.

Note for whoever picks this up: the reason 478 tests miss it is the same shape as T8.3's finding.
Every keyboard test configures both sides at 24 and therefore asserts the composition at the one
ratio where the bug cancels out. The tests encode the default, not the invariant.
