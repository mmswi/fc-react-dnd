# T7.2 — `src/sortable-list.tsx`

**Phase** P7 — Sortable list · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Scope a set of sortable items to one list and hand the consumer the only thing they
actually want at the end: `onSortEnd({ activeId, fromIndex, toIndex })`.

## Test first

Red tests before implementation:

- `onSortEnd` fires once on a same-list drop, with indices computed from the **final
  projection** — assert `fromIndex`/`toIndex` against a hand-checked scenario, not against
  whatever the implementation produces.
- A drop that lands back at the origin index does **not** fire `onSortEnd` (or fires with
  equal indices — pick one, document it, and pin it with a test; consumers will build
  undo stacks on this).
- A drop **outside** the list, or onto a different `SortableList`, does not fire it —
  cross-list moves are explicitly Backlog.
- Escape mid-drag fires no `onSortEnd`.
- The context value is stable across re-renders, so items don't re-render because the list
  did.
- Two sibling lists in one provider stay independent.

## Acceptance criteria

- Exports `SortableList` + `SortableListProps`; subpath `fc-react-dnd/sortable-list`.
- **`onSortEnd` must report enough to place the item without trusting stale indices.**
  `{ activeId, fromIndex, toIndex }` is purely positional, and the consumer applies it to
  whatever their list is at drop time — which a concurrent edit may have changed underneath
  the drag. Carry the id-relative landing position too (the neighbour the item lands
  after/before) so the consumer can place it correctly when indices have shifted. Adding a
  field later is a breaking-ish API decision; getting it right now is free. See
  [`ANALYSIS.md`](../ANALYSIS.md) § A6 and the parallel change in
  [T8.1](T8.1-tree-math.md).
- Provides per-list context: `listId` and `direction` (`vertical` | `horizontal`).
- Computes the result through `useDndMonitor` ([T4.4](T4.4-use-active-drag-and-monitor.md)),
  so the list itself does not re-render during the drag.
- `'use client'` at the top.

The list computes its result through `useDndMonitor`, so it never re-renders during a drag. It
reads the **final projection** rather than reconstructing one — drag events fire before the
store resets ([T3.1](T3.1-store.md)), so `projectList(store.getState(), …)` inside `onDragEnd`
is the same projection the items were rendering from a moment earlier.

### The decision the criteria left open: a no-op drop fires nothing

`onSortEnd` does **not** fire when `fromIndex === toIndex`. Consumers build undo stacks on this
event, and an entry that undoes to the same order is worse than no entry at all. Documented in
the TSDoc and pinned by a test.

The same rule covers three cases at once, because all three project `toIndex === fromIndex`: a
drop back at the origin, a drop over nothing, and a drop over an item belonging to a *different*
`SortableList`. Cross-list moves are Backlog, and the important part is that neither list
invents a result for a drop it cannot describe — asserted with two lists in one provider.

### `SortEndEvent` carries ids as well as indices

`{ activeId, fromIndex, toIndex, afterId, beforeId }`. Indices are positional and the consumer
applies them to whatever their list is at drop time, which a concurrent edit may have changed
underneath the drag; ids survive that (§ A6). `afterId`/`beforeId` are computed against the
order **with the active item removed**, so they name the two rows it lands between. Both ends of
the list are tested, where one of them is `null`.

### The context lives in `internal/sortable-context.ts`

So `SortableList` and `useSortable` can both reach it without one public subpath importing
another. Its value is memoised on `[listId, direction, items]` — all stable if the consumer
honours the `items` stability contract — and the stability itself is asserted across a forced
parent re-render.
