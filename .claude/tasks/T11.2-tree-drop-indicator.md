# T11.2 — Ship the drop indicator, don't just describe it

**Phase** P11 — Defects found after v0.1 · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Ship a `TreeDropIndicator` component so a consumer gets tree drag feedback by installing the
library, not by reading a recipe and reimplementing it.

## Why

Raised by the user (2026-08-09), looking at commit `3e22506`:

> these are fixes applied in the playground. how will the users of this library know to apply
> this fix by just installing it?

They are right, and the gap is worse than the tree overlay that commit added. **Tree rows are
measure-only and never move, by design** — translating them would move the geometry the
projection is computed from. So a tree wired up from the library's own API renders *nothing* on
drag: no motion, no line, no ghost. It does not look minimal, it looks broken. That is exactly
the report this repo already got once ("the tree dnd is like shit, unpredictable"), and the fix
landed in `playground/` where no consumer can reach it.

The library computes everything needed and hands back `projection.indicator`
({ `rowId`, `edge`, `depth` }) — then stops one step short of the thing every consumer must
build. That is the same "reports the gesture, not the outcome" boundary this whole project
exists to cross, reappearing one level up in the rendering layer.

**Already done, and not enough:** [T10.1](T10.1-readme.md)'s tree example now renders both the
indicator and a `DragOverlay`, and states that rows do not move. Docs make it discoverable;
they do not make it correct. The screen-space derivation was got wrong three times *by this
repo's own demo* before `indicator` existed — a consumer with less context will do no better.

## The design worth trying first

**Zero contract on the consumer's markup.** During a drag the store already holds
`measuredRects`, so the component can position itself in viewport coordinates from
`measuredRects.get(indicator.rowId)` and needs no `position: relative` ancestor, no row height,
and no indent constant beyond the one it already has:

```tsx
<DndProvider>
  <MyTree />
  <TreeDropIndicator />      {/* reads the live projection; renders null when there is none */}
</DndProvider>
```

Open questions for whoever takes it:

- Where does it read the projection from? `useTreeDrop` owns it and is called inside the
  consumer's component. Either the component takes `projection` as a prop (honest, one line at
  the call site) or the projection is published to the store the way § A11 publishes the
  indent. Prop first — a store round-trip needs a reason.
- Does it portal, like `DragOverlay`? Probably the same treatment, and `portalContainer` is
  already a Backlog item for both.
- Styling surface: thickness and colour as props, or a `className`, or CSS custom properties.
  Keep it to the smallest thing that lets a design system in.

## Acceptance criteria

- A tree built from the README example minus the hand-rolled indicator still shows a correct
  line/box for `between`, `into`, and an un-nest that lands below a whole subtree.
- Renders nothing when the projection is `null` — the no-legal-position case.
- No DOM reads in the move path: position comes from the cached rects, not from
  `getBoundingClientRect` (perf invariant 1).
- Re-renders only when the indicator actually changes, not per pointermove
  (`treeProjectionsAreEqual` already compares the three indicator fields).
- The playground uses the shipped component and deletes its hand-rolled one — **the demo must
  not keep a private implementation of the thing consumers are told to use.**
- A public subpath + task-file entry per `CLAUDE.md` § "Public API policy".

## Where it stands

Not started. Opened 2026-08-09.

**Note for whoever takes it:** the playground and the README currently disagree about *how* to
draw the indicator, which is its own small defect. The playground positions absolutely against
a shared `position: relative` container using a fixed `ROW_HEIGHT_PX`; the README example
positions against each row with no height assumption, which is the better recipe. Shipping the
component makes both obsolete, so do not spend time reconciling them first.
