# T4.1 — `src/dnd-provider.tsx`

**Phase** P4 — React API · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

The single public component consumers mount. It owns one store instance, wires sensors,
collision, auto-scroll and accessibility, and forwards drag events to callbacks — while
itself never re-rendering during a drag.

## Test first

Red tests before implementation:

- **One store per instance, created once.** Assert the store identity is stable across
  re-renders and that StrictMode's double-invoked effects don't produce two stores or two
  subscriptions (perf invariant 8).
- **The provider does not re-render during a drag.** Render counter on the provider;
  drive a full drag; assert the count doesn't move (perf invariant 4). This is the whole
  architectural claim, so it gets an explicit test.
- **Latest-props sync.** Change `onDragEnd` to a new closure mid-drag; assert the drop
  calls the *new* one, and that doing so did not tear down the drag.
- Sensors are attached on mount and detached on unmount, once each.
- Nested providers keep separate state.

## Acceptance criteria

- `DndProvider` + `DndProviderProps` exported; subpath `fc-react-dnd/dnd-provider`.
- Store created per instance (never module-level).
- Props: `sensors`, `collisionDetection` (defaulting to `closestCenter`), `autoScroll`,
  `accessibility`, and the `onDragStart` / `onDragMove` / `onDragOver` / `onDragEnd` /
  `onDragCancel` callbacks.
- **`onDragCancel` carries a `DragCancelReason`** — `'escape' | 'blur' | 'pointer-cancelled'
  | 'item-removed'` ([T2.1](T2.1-public-types.md)). A drag can be cancelled *by the library*
  when a registered node disappears mid-drag ([`ANALYSIS.md`](../ANALYSIS.md) § A6) or when the
  browser revokes the interaction ([T5.1](T5.1-pointer-sensor.md)), and a consumer showing
  "another editor changed this list" must be able to tell those from a user pressing Escape.
  **Assert all four reaching the callback** — an untested member is one that quietly regresses
  to `'escape'`.
- Callbacks read through a latest-props ref so changing a handler mid-drag neither
  restarts the drag nor calls a stale closure.
- Renders the live region and the hidden instructions element from
  [T6.3](T6.3-accessibility-internals.md).
- `'use client'` at the top.

### Deviations from the criteria, and why

**No `autoScroll` prop yet.** It is listed above, but a prop that is accepted and does nothing
is a lie in the API — worse than a missing one. **Added at [T6.2](T6.2-auto-scroll.md)**
(default `true`), along with the test that it drives the loop and that switching it off stops
it.

**`sensors` defaults to a frozen empty array, not to `[pointerSensor(), keyboardSensor()]`.**
Neither sensor exists yet. **Resolved at [T5.2](T5.2-keyboard-sensor.md)**: the default is now
`Object.freeze([pointerSensor(), keyboardSensor()])`, per [`ANALYSIS.md`](../ANALYSIS.md) § A9.5.

**"Sensors are attached on mount and detached on unmount" does not apply to this design.** A
sensor produces *activator props*; it owns window/document listeners only for the duration of
one interaction ([T5.1](T5.1-pointer-sensor.md)), so there is nothing for the provider to
attach or detach. The provider's job is to carry the sensor list to `useDraggable`, which is
what is tested here; activator merging is [T4.2](T4.2-use-draggable.md)'s test.

**The tests drive the store the provider created**, reached through a context probe, because
`useDraggable` ([T4.2](T4.2-use-draggable.md)) and the pointer sensor
([T5.1](T5.1-pointer-sensor.md)) do not exist yet. [T4.5](T4.5-react-api-component-tests.md)
and [T9.1](T9.1-integration-pointer-flow.md) drive the same flows through the fully public API
once they do.

### `sensors` is in the context value, which makes it a stability contract

The alternative was a stable getter over a ref, which would mean reading a ref during render.
Instead the array is a context dependency, the default is a module-level frozen constant (so
every consumer who does not customise gets perfect stability), and a consumer who *does* pass
`sensors` owns keeping it referentially stable. That is the same documented-contract shape the
library already uses for `items` in [T8.2](T8.2-use-tree-drop.md) (§ A7 F6), with the same
failure mode: an inline array re-renders the subtree on every parent render.

The `useMemo` deps are otherwise the store, a `useId` result, and two plain strings — nothing
that churns. `accessibility` is read as primitives (`?.instructions`,
`?.draggableRoleDescription`) precisely so an inline `accessibility={{ … }}` object cannot
churn the context.

### The instructions element lives in `src/internal/live-region.tsx`

That file is [T6.3](T6.3-accessibility-internals.md)'s, and it is created here holding only the
visually-hidden style and `DragInstructions` — because
[T4.2](T4.2-use-draggable.md)'s `aria-describedby` needs the element to exist *now*, and
duplicating the visually-hidden style rather than sharing it would be the worse trade. T6.3
adds the announcement region to the same file, plus `announcements.ts` and the tests for both.
Asserted here already: the element is `position: fixed` and off-screen but neither
`display: none` nor `hidden` — either would remove it from the accessibility tree, i.e. from
exactly the users it exists for.
