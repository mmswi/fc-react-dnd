# T7.1 — `src/internal/list-projection.ts`

**Phase** P7 — Sortable list · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Answer "where would this item land, and how far does every other item shift?" as **pure
math over cached rects** — computed once per store-state version and read by O(1)
selectors, never recomputed per subscriber (perf invariant 9).

## Test first

Red tests before implementation, on hand-built rect fixtures:

- Item order is derived from cached rects along the list axis, for both `vertical` and
  `horizontal`.
- Projected index of the active item, including the two ends and the no-op case (dragging
  an item onto itself projects its own index and produces zero translates).
- Per-item translate: items between the origin and the projection close the gap; the rest
  don't move. Assert exact values, not just signs — an off-by-one here is a visible
  stutter.
- Items of **unequal size** produce correct translates (equal-height fixtures hide the
  most common bug in this math).
- **Memoization:** calling the projection twice with the same state object returns the
  **identical reference** and recomputes once; a new state object recomputes. This is the
  test that protects perf invariant 9 — a WeakMap keyed by the immutable state object from
  [T3.1](T3.1-store.md).

## Acceptance criteria

- Pure: no DOM, no React, no `'use client'`.
- Memoized once per store-state version via a WeakMap keyed on the state object; per-subscriber
  reads are O(1).
- **The WeakMap key must be the per-provider store state object — never consumer-supplied
  data** (the `items` array, a node, a props object). The memo map is module-level, so an
  identity shared across two `DndProvider`s would make them overwrite each other's entry:
  last writer wins, and the symptom is a wrong projection in whichever provider rendered
  second. Store state objects are minted per provider and cannot collide; consumer arrays
  can and do. This is exactly the slate-react `NODE_TO_PARENT` bug — same global registry,
  same identity collision, same silent corruption. See [`ANALYSIS.md`](../ANALYSIS.md) § A5.
- **Regression test:** render the *same* `items` array into two sibling providers, drag in
  both, assert each gets its own correct projection.
- Handles both list directions; direction comes from the `SortableList` context, not a global.
- Named constants for any threshold.

### The memo is two-level, and the criteria's single level would have been wrong

The criteria say to key the WeakMap on the store state object and never on consumer data, and
the reason given is sound: a module-level map keyed on an identity shared between two
`DndProvider`s makes them overwrite each other's entry, which is the slate-react
`NODE_TO_PARENT` bug (§ A5).

But keyed on the state **alone**, two `SortableList`s inside *one* provider collide the same
way — they share a single state object. So the outer key stays the state object (per provider,
cannot collide) and the inner key is the list's own `itemIds` array. Same shape as § A7 F6
prescribes for the tree, arriving here from the two-lists-one-provider direction instead of the
two-providers direction. Both regression tests are present.

`direction` is stored beside each entry and compared rather than keyed on, so re-projecting the
same items along a different axis recomputes instead of returning the wrong answer.

### The translate maths, and the bug the unequal-size fixture caught

The first implementation moved each displaced item to **where its predecessor was**. That is
correct only when every row is identical and flush against the next, which is exactly what an
equal-height fixture cannot reveal — and the criteria call out for that reason.

With rows of 20, 60, and 30, removing the first slides the other two up by **20** (the space it
vacated), not by 60 (the predecessor's height). The implementation now expresses both halves in
terms of the active item's own footprint:

- moving forward: displaced items shift by `-(start[from+1] - start[from])` — the active item's
  size plus the gap that followed it
- moving backward: displaced items shift by `+(size[active] + gapBeforeActive)`
- the active item lands at `start[to] + size[to] - size[active]` going forward, or `start[to]`
  going backward

The landing expression needs no gap term: the shift and the gap cancel out of it. That is
noted in the code because it reads like something is missing.

**The test was wrong too.** It expected the dragged item to land at 70 in the unequal case;
working the layout through by hand gives `b[0,60), c[60,90), a[90,110)` — 90. Two independent
errors that happened to disagree, which is the argument for deriving expected values from a
worked example rather than from whatever the implementation prints.
