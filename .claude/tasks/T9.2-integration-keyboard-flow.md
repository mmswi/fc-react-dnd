# T9.2 — Integration: the full keyboard flow

**Phase** P9 — Integration & verification · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

The same end-to-end proof as [T9.1](T9.1-integration-pointer-flow.md), for the keyboard
path — including the announcements, which are the part a sighted developer never notices
breaking.

## Acceptance criteria

- Drives real keyboard events on a focused handle: Space/Enter to pick up → arrows across
  droppables → Space/Enter to drop.
- Callback order and payloads asserted as a sequence, matching the pointer flow's shape —
  a consumer should not be able to tell which sensor drove the drag from the events alone.
- **Announcement texts asserted** from the live region's DOM at each stage: pickup, each
  target change, drop (accessibility invariants 1, 2).
- Escape mid-drag → cancel path + cancel announcement; blur mid-drag → same.
- Arrow into empty space (no droppable in that direction) leaves the target unchanged.
- Runs inside `<StrictMode>`.

## Where it stands

`src/integration.keyboard.test.tsx` on disk (2026-08-08); 11 tests green, all inside
`<StrictMode>`.

The callback sequence is deliberately asserted to be **the same shape** the pointer flow
produces — `['start', 'over', 'end']` — which is the property that matters: a consumer should
not be able to tell which sensor drove a drag from the events alone. Both files also assert the
`start.over` addition [T9.1](T9.1-integration-pointer-flow.md) found.

Announcements are read from the live region's DOM at each stage: pickup names the item, each
target change is announced **in both directions** (down to Archive, back up to Inbox), the drop
names where it landed, and Escape and blur both produce the cancel text with the right
`DragCancelReason` on the event.

Arrow into empty space leaves the target unchanged — asserted by the callback sequence not
growing rather than by reading state.
