# T3.3 — `src/internal/context.ts`

**Phase** P3 — Store & subscription layer · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Carry the per-provider store handle down the tree — and nothing else. The context value
must be **stable for the provider's lifetime**, because a changing context value would
re-render the entire subtree on every drag and undo the whole architecture.

## Test first

Red tests before implementation:

- A consumer outside any `DndProvider` gets a clear, named error — not
  `undefined is not an object` from three frames deeper.
- The context value is referentially stable across provider re-renders (assert identity
  across a forced parent re-render). **This is the single most load-bearing test in P3.**
  Context compares with `Object.is` per consumer (`ReactFiberNewContext.js:465-486`); on a
  change, propagation sets `lanes` directly on every consumer fiber and walks up setting
  `childLanes` (`:245-254`), which is exactly what `bailoutOnAlreadyFinishedWork` re-checks
  — the bailout is undone by its own bookkeeping. And there is **no downstream mitigation**:
  `memo` cannot stop context propagation, proven by repro against plain `memo`,
  `memo(fn, () => true)`, and `shouldComponentUpdate() { return false }` — all three bail
  out, all three let their consumer re-render. If this value churns, no amount of `memo` on
  list items saves the drag. See [`ANALYSIS.md`](../ANALYSIS.md) § A3.5.
- Two sibling providers hand their subtrees two different stores — no cross-talk.

## Acceptance criteria

- Context carries the store handle only; drag state is read through
  [T3.2](T3.2-use-store-selector.md), never through context.
- A small `useDndStore`-style accessor throws a named, actionable error when used
  outside a provider.
- `'use client'` at the top (it touches React context).
- No module-level store — SSR-safe and multi-provider-safe by construction.

## Where it stands

### The value carries three things, not one

The criteria say "the store handle only". It also carries `instructionsId` and
`draggableRoleDescription`, because `useDraggable`'s `handleProps` needs both for
`aria-describedby` and `aria-roledescription` (accessibility invariant 3) and there is no
other channel to them. The criterion's actual intent — **nothing that changes during a drag**
— is preserved exactly: all three are fixed for the provider's lifetime.

`draggableRoleDescription` is a plain string from the `accessibility` prop, so
[T4.1](T4.1-dnd-provider.md) memoises the value on primitive dependencies. If a consumer does
change it, the subtree re-renders once, which is correct — every handle's aria text genuinely
changed. The A3.5 hazard is a churning *identity*, not a value that legitimately differs.

### `useDndContext(hookName)` takes the caller's name

So the error says `useDraggable() was called outside a <DndProvider>` rather than naming an
internal the consumer has never heard of. Asserted three ways: the message contains the
package name, the hook name, and `DndProvider`.

### The A3.5 pair, and the vacuous-test trap it walked into

Two matched tests state the constraint the architecture rests on: a churning context value
re-renders every consumer **even one wrapped in `memo`**, and a stable one leaves them alone
across a parent re-render. Together they say context stability is the floor and there is no
downstream rescue.

Both initially passed for the wrong reason — the forced parent render was called outside
`act()`, so nothing flushed and neither assertion could ever fail. The red run caught it
because the churning case *expected* a change and got none. Wrapping both in `act()` made them
real. Worth remembering for every later render-count test in this repo: **a render-count
assertion with an unflushed update is vacuous in whichever direction it is written.**
