necessary and not sufficient — and capture the render-count numbers the blog post will
quote.

  Chrome session.

  errors.

  indicator — named meaningfully, for the blog post.

  for a defined scenario (state the item count, the drag distance, and the number of
  boundary crossings, so the measurement is reproducible).

- Any disagreement with the asserted counts in [T7.4](T7.4-sortable-granularity-tests.md) is
  investigated, not averaged away.

## Where it stands

Run in a real Chromium browser (Brave) against `bun run --filter playground dev` on
**2026-08-08**. Everything except the animated GIF is captured; that one item is recorded as
outstanding below rather than approximated.

### The numbers — measured, three times, identical

**Scenario, stated so it can be re-run:** the Comparison page, **24 items** per list, dragging
item-1 down onto item-4 — **154 px**, **3 boundary crossings**, **40 pointermove events**. The
same synthesised pointer path is dispatched to both lists in the same session, so the two are
like-for-like. Commits come from a `<Profiler>` wrapped around **each row**, so the counts are
React's own, not a proxy.

| During the drag (40 moves, 3 crossings) | Rows that committed | Total commits |
| --- | --- | --- |
| **fc-react-dnd** | **4** of 24 | **9** |
| **dnd-kit 6.3.1 / sortable 10.0.0** | **24** of 24 | **96** |

| On the drop (the consumer's own reorder) | Rows | Commits |
| --- | --- | --- |
| fc-react-dnd | 24 | 24 |
| dnd-kit | 24 | 48 |

Repeated three times back to back with **identical** results each run.

**Cross-check against [T7.4](T7.4-sortable-granularity-tests.md): they agree exactly.** T7.4
asserts 3 commits per boundary crossing in jsdom; 3 crossings × 3 = 9, which is what the browser
measured. Two independent measurements of the same claim, in two environments, matching to the
integer. No discrepancy to investigate.

### Console: clean

Six messages across the whole session, all of them Vite's own `[vite] connecting…` /
`[vite] connected.`. No React warnings, no StrictMode complaints, no listener errors — with
every page inside `<StrictMode>`.

### What was exercised

Pointer drags on the sortable, tree and comparison pages; keyboard drags on the tree. The tree
specifically:

- **Drop-into** — "Meeting notes" dropped onto the leaf "Onboarding", which gained a `children`
  array and an expand arrow. § A7 D2's any-document-can-parent rule, visible.
- **Drop-between** — "On-call" moved out of Engineering to `(parent: handbook, index 0, depth 1)`.
- **Cycle prevention** — dragging "Handbook" onto its own descendant "Style guide" left the tree

- **Keyboard** — Space to pick up, arrows to move, live projection readout showing
  `{ parentId: "onboarding", index: 0, depth: 2, mode: "between", afterId: null, beforeId: null }`,

  announcements working, which is § A7 F9's requirement.

Still captured: `docs/assets/tree-keyboard-projection.jpg` — a keyboard tree drag with the drop
indicator and the projection readout together. That single frame is the library's whole argument
in one picture: not "you are hovering over On-call" but `(handbook, index 0, depth 1)`.

### One defect found and fixed, in the demo

The drop indicator was drawn one row too low when a projection had `afterId: null` and a
`beforeId` — "before X" was being rendered as "after X". Fixed by anchoring the indicator to
`afterId` **below** its row and to `beforeId` **above** it.

## Amended 2026-08-08 (later the same day) — the numbers above are superseded

The user tested the demo and reported ours felt **janky** where dnd-kit felt smooth. They were
right, and their screenshots showed why: dnd-kit's dragged row carried **121** commits, ours **8**.
That gap was not a win. It was the defect.

### What was wrong

`useSortable` gave the dragged row its *projected landing slot*. So it teleported a whole
row-height at a time instead of moving with the pointer. The 9-commit figure this task originally
recorded was bought by not animating the thing the user is holding.

Fixed in `use-sortable.ts`: the dragged row now follows the pointer, and `trackTransform: false`
opts back into the old behaviour for consumers whose `DragOverlay` carries the motion.

### Re-measured, same scenario, three runs, identical

| During the drag | Rows that re-rendered | Total commits |
| --- | --- | --- |
| fc-react-dnd | **4** of 24 | 44 |
| dnd-kit | **24** of 24 | ≥96 |

### And the original methodology had a flaw worth recording

The measurement tab reports `visibilityState: 'hidden'` and **0 rAF frames in 300 ms** — Chrome
throttles `requestAnimationFrame` to nothing in a background tab. dnd-kit schedules part of its
per-move work through rAF; this library schedules on React's sync lane, which flushes in a
microtask and is unaffected.

So the two were never measured on equal terms, and **the error favoured dnd-kit**: its total is a
floor, ours is complete. That direction is safe for a claim, but the totals should not be quoted
against each other, and the README no longer does. The honest comparison is **rows that
re-rendered**, which does not depend on scheduling at all: 4 versus 24.

A future run wanting comparable totals must foreground the tab.
