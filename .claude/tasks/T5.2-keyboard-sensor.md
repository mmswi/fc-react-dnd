# T5.2 — `src/keyboard-sensor.ts`

**Phase** P5 — Sensors · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

A first-class keyboard drag — not an afterthought (accessibility invariant 1). The design
that makes this cheap: arrow keys produce a **transform**, exactly like a pointer would,
so keyboard drags flow through the same collision and the same tree-depth math rather than
a parallel code path.

## Test first

Red tests before implementation:

- Space and Enter both pick up a focused draggable; a second press drops it.
- Arrow keys move to the **nearest droppable in that direction**, using
  `findDroppableInDirection` from [T2.2](T2.2-geometry.md) — including the case where
  there is nothing in that direction (stay put, don't wrap, don't jump across the page).
- **The targeting query includes measure-only rects** ([T3.1](T3.1-store.md)): tree rows are
  not droppables, but keyboard vertical navigation must still step through them. Collision
  stays droppables-only; targeting reads the whole rect cache.
- **Tree reachability composes from here** (§ A7 F9): vertical steps move through row
  positions, ArrowLeft/Right walk the depth ladder via the same ±indent transforms, and
  every legal tree outcome must be reachable — the invariant test lives in
  [T8.2](T8.2-use-tree-drop.md); this sensor must not hard-code any tree knowledge to make
  it pass.
- **ArrowLeft / ArrowRight double as ±indent**, emitting a horizontal transform step. This
  is the seam that gives the tree its keyboard depth control in
  [T8.2](T8.2-use-tree-drop.md) — assert the transform, not a tree-specific side effect,
  so the sensor stays tree-agnostic.
- Escape cancels; **blur cancels** (a drag must not survive the user tabbing away).
- `scrollIntoView` is called when the target changes, so the keyboard drag stays visible.
- Teardown after drop, cancel, and unmount-mid-drag leaves no listener behind.

## Acceptance criteria

- Exports `keyboardSensor` + `KeyboardSensorOptions`; subpath `fc-react-dnd/keyboard-sensor`.
- Activation keys `preventDefault` (perf invariant 6) so Space doesn't scroll the page
  mid-drag.
- Indent step is a named constant, overridable through options.
- Emits the same announcements pipeline as the pointer path
  ([T6.3](T6.3-accessibility-internals.md)).
- `'use client'` at the top.

### Arrow semantics: vertical navigates, horizontal indents. No layout-dependent branch

The criteria state two things that cannot both be literal for all four keys — "arrow keys move
to the nearest droppable in that direction" and "ArrowLeft/ArrowRight double as ±indent".
Resolved by axis:

- **ArrowUp / ArrowDown** call `findTargetInDirection`, which reads the whole rect cache and so
  steps through measure-only tree rows as well as droppables.
- **ArrowLeft / ArrowRight** always emit `translate.x ± indentPx`. Always, with no targeting.

The rejected alternative was "target if something is there, otherwise indent". It reads well
and breaks quietly: tree rows *are* in the rect cache, and an indented row's centre is offset
horizontally, so ArrowRight in a tree would sometimes jump to a child row instead of changing
depth — depending on whether the consumer's indentation is padding or margin. A rule that
depends on someone's CSS is not a rule.

The consequence is that a **horizontal** `SortableList` steps by `indentPx` rather than
target-to-target under the keyboard. Recorded as a Backlog entry rather than papered over.

The sensor stays entirely tree-agnostic: it emits a horizontal translate, and it is the tree
projection that decides a horizontal translate means depth.

### All key handling stays on the handle, not on `window`

A `window` keydown listener added during React's own `onKeyDown` still receives that same
event afterwards — React 19 attaches at the root container, which is below `window` — so the
activating Space would immediately end the drag it just started. Since focus stays on the
handle for the whole of a keyboard drag by construction, handling everything in the handle's
`onKeyDown` avoids the problem instead of working around it. Only `blur` is a native listener,
on the handle itself.

### `DragSession` gained `isActive()` — a fifth member, and a real bug it fixes

A drag can end without the sensor being told: the store cancels when a registered node
disappears (§ A6), and the keyboard path has **no trailing event** that would reveal it — unlike
the pointer sensor, which always gets a `pointerup`. Left believing a drag was running, the
sensor consumed the user's next Space ending a drag that was already over, so the pickup
appeared to do nothing.

Written test-first (the red test asserted two `onDragStart` calls and saw one), then fixed by
adding `isActive()` to the session and checking it at the top of the key handler.
[T2.1](T2.1-public-types.md)'s type test is updated to pin all five members.
