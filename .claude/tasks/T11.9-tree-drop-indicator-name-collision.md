# T11.9 — Two public-surface corrections: a name collision, and a field nobody reads

**Phase** P11 — Defects found after v0.1 · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

Both are breaking changes to the published surface, which is why neither could land in
[T11.8](T11.8-readability-rewrite.md) — that task's whole safety argument was that the surface
could not move, guarded by `src/public-api.test.ts`.

**All file:line references below are as of the end of T11.8 (2026-08-11).** Re-derive before
coding; T11.8 moved a lot of code, and T11.7 is a standing example of what stale ones cost.

## Part 1 — `TreeDropIndicator` names two different things

One exported name currently resolves to two unrelated exports:

| | |
| --- | --- |
| `src/tree.ts:132` | `export type TreeDropIndicator` — the screen anchor `{ rowId, edge, depth }` |
| `src/tree-drop-indicator.tsx:37` | `export const TreeDropIndicator` — the React component that draws it |

Both are published: `fc-react-dnd/tree` and `fc-react-dnd/tree-drop-indicator`. This is the
`mihai-coding-standards` rule *"One name, one meaning — don't share it between a type and a
component"*, verbatim — the skill's own example is a type and a component both called
`AuthProvider`.

## Why it matters here

TypeScript keeps types and values in separate namespaces, so this compiles. The cost is on the
reader and the editor: `TreeDropIndicator` in an import list says nothing about whether it is a
shape or something you render, and auto-import will resolve it to whichever subpath it indexed
first. A consumer who wanted the component and got the type sees an error far from the cause.

## The fix, and why it is not in T11.8

The standards' resolution: the value keeps the name that reads at the call site, the type gets the
name for the concept it describes — so `TreeDropIndicator` stays the component, and the type
becomes `TreeDropAnchor` (or `TreeIndicatorPlacement`; pick at implementation time). `edge` and
`depth` describe *where to draw*, so an anchor name is the honest one.

Renaming an export is an API decision, which `CLAUDE.md` § "Public API policy" requires be its own
task.

## Part 2 — `SensorContext.draggableId` is written by everyone and read by no one

`types.ts:207` declares it, `use-draggable.ts:103` and `use-tree-drop.ts:152` both fill it in, and
**nothing consumes it** — neither `pointerSensor` nor `keyboardSensor`, nor the playground:

```
$ grep -rn "draggableId" src playground/src --include='*.ts' --include='*.tsx' | grep -v '\.test\.'
src/types.ts:207:  readonly draggableId: DndId
src/use-draggable.ts:103:        draggableId: id,
src/use-tree-drop.ts:152:          draggableId: id,
```

It is a field on a public contract that exists for nobody, and a reader tracing the sensor seam
will go looking for the consumer that justifies it. The condition predates T11.8; that task made
it *visible* by moving the context object from one hidden mint site to two explicit call sites.

Decide between two honest outcomes rather than leaving it:

- **Drop it.** `SensorContext` becomes `{ beginDrag }`. Breaking only for a custom sensor author
  who reads a field that tells them nothing they cannot get from the handle they were attached to.
- **Keep it and give it a job** — the natural one is letting a sensor identify *which* draggable it
  was activated for when one sensor instance serves many handles. If that is the intent, a comment
  saying so is the minimum, since the shipped sensors demonstrate the opposite.

## The red test

`src/public-api.test.ts` (added by T11.8) pins the runtime export names of all 13 subpaths, and
its `PublishedTypeSurface` block pins the type names under `tsc --noEmit`. Change the pinned type
name there first and watch the typecheck fail, then rename.

## Acceptance criteria

- No name is declared by two different public exports. Verify with the sweep T11.8 used:
  duplicate declared names across non-test `src/` reduce to the module-private ones
  (`CacheEntry`, `NO_DATA`, `computeProjection`, `projectionCache`), which are not importable.
- Every field of `SensorContext` has a consumer in `src/`, or a comment saying who it is for.
- `CHANGELOG.md` records both as breaking changes under a new version heading.
- README and `docs/` updated wherever either is named.
- `bun run verify` green.
