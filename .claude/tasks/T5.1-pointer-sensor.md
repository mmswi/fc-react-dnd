# T5.1 — `src/pointer-sensor.ts`

**Phase** P5 — Sensors · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Translate pointer events into store lifecycle calls, with an activation threshold so a
click is still a click. The sensor owns its window/document listeners for exactly one
interaction and tears down completely afterwards.

## Test first

Red tests before implementation, driving real DOM events:

- **Activation by distance** (the default): moving less than the threshold starts nothing;
  crossing it starts exactly one drag.
- **Activation by delay + tolerance**: holding for the delay activates; moving beyond the
  tolerance before the delay cancels instead of activating.
- **Escape cancels** mid-drag, and the store's cancel path runs (not the end path), reporting
  reason `'escape'`.
- **`pointercancel` cancels** — the browser fires it when it takes the interaction away: a
  touch reinterpreted as a scroll or system gesture, a device rotation, a pen leaving range.
  Unhandled, the drag **never ends** — `activeId` stays set, document listeners stay bound,
  and the overlay stays on screen until the page reloads. On touch this is not an edge case;
  it is what happens whenever the browser decides the drag was a scroll. Route it through the
  same cancel path with reason `'pointer-cancelled'`, and assert full teardown, since this is
  the cancel most likely to leak. See [`ANALYSIS.md`](../ANALYSIS.md) § A6.
- **Click suppression**: after a real drag, the trailing `click` is suppressed; after a
  non-activating press, the click goes through untouched. Both directions get a test —
  suppressing a legitimate click is the more annoying bug.
- **Teardown**: after end, cancel, and unmount-mid-drag, no document/window listener
  survives. Assert by counting listeners, not by hoping (perf invariant 7).
- **Second pointer while dragging is ignored** — a touch with a second finger must not
  start a second drag or hijack the first.
- `user-select` is locked during the drag and restored after, including after cancel.

## Acceptance criteria

- Exports `pointerSensor` + `PointerSensorOptions`; subpath `fc-react-dnd/pointer-sensor`.
- Implements the `Sensor` contract from [T2.1](T2.1-public-types.md) and drives a
  `DragSession`; a stale session after end/cancel is a no-op (guaranteed by
  [T3.1](T3.1-store.md), asserted here).
- Listeners passive except the activated `pointermove`, where `preventDefault` is
  load-bearing (perf invariant 6).
- Every tunable is a named constant (`DEFAULT_ACTIVATION_DISTANCE_PX`, delay, tolerance).
- `'use client'` at the top.

## Where it stands

`src/pointer-sensor.ts` + tests on disk (2026-08-08); 20 tests green, subpath
`./pointer-sensor` added, `bun run verify` clean. Every red test above has a green
counterpart.

### The activating move is reported immediately

The first draft activated on the move that crossed the threshold and then waited for the
*next* event to report a translate. The "translate measured from where the press started" test
caught it — `onDragMove` had never fired. So activation now reports that same move straight
away, and the item is under the pointer on the first rendered frame instead of one event
behind it. It is reported directly rather than by re-entering the dragging handler, because
the pre-activation listener is **passive** and calling `preventDefault` from it would earn
nothing but a console warning.

The drag still *begins* from the press point, not from where the threshold happened to be
crossed — otherwise every drag would jump by the activation distance on its first frame.

### Listener passivity, asserted rather than asserted-in-prose

Two `pointermove` listeners, swapped at activation: passive before (this sensor never calls
`preventDefault` there), non-passive after (`preventDefault` is load-bearing — without it the
browser selects text and scrolls under the drag). The test records the `options.passive` value
each registration was made with, so perf invariant 6 is a number.

### Teardown is counted by (type, function) pairs, not by a per-type counter

The first tracker counted registrations per event type and went **negative**, because
`teardown` removes every listener type unconditionally and removing one that was never added
is a DOM no-op. A negative balance reads as a leak. Tracking pairs and only decrementing on a
match fixes it.

**One listener deliberately outlives the drag**: the capture-phase `click` swallower, for
exactly one macrotask. Long enough to eat the click the browser fires after a real drag's
`pointerup`, and no longer — otherwise a drag that ended over nothing clickable would go on to
eat the user's next legitimate click. Both teardown tests await that macrotask before counting,
and there is a separate test that a *second* click gets through.

### Second-pointer and stale-session behaviour

One `Interaction` at a time for the whole sensor instance, and every handler checks
`event.pointerId` against it. A second finger landing mid-drag starts nothing and changes no
translate — both asserted. When the store cancels underneath the sensor (a row removed
mid-drag, per A6), the session's token makes `end()` a no-op and the sensor still tears its
listeners down on the trailing `pointerup`; that path has its own test.
