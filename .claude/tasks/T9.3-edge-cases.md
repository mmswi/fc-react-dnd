# T9.3 — Edge cases

**Phase** P9 — Integration & verification · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

The situations that turn a demo-quality drag-and-drop library into a production one. Every
one of these has bitten a real library; each gets a test that would fail loudly.

## Acceptance criteria

Each case tested through the public API, inside `<StrictMode>`:

- **Disabled draggable** — keeps `aria-disabled`, has no activation listeners, pointerdown
  and Space both start nothing (accessibility invariant 4).
- **Disabled droppable** — never becomes `over`, never wins collision.
- **Escape mid-drag** — cancel path runs, `onDragEnd` does **not** fire, transforms reset,
  announcement is the cancel text.
- **Draggable unmounts mid-drag** — the drag ends cleanly, no listener leak, no crash from
  a dangling node reference. (Assert on listener counts and registry size, not on the
  absence of a thrown error.)
- **Droppable unmounts mid-drag** — `over` clears rather than pointing at a removed id.
- **Second pointer while dragging** — ignored; the first drag continues unaffected.
- **Provider unmounts mid-drag** — everything torn down: listeners, rAF loops, subscriptions
  (perf invariant 7).
- **Scroll during a drag** — the dirty flag re-measures and `over` updates without the
  pointer moving.

**Concurrent mutation** — a collaborator deletes a row mid-drag, modelled as the consumer
re-rendering with fewer items (see [`ANALYSIS.md`](../ANALYSIS.md) § A6). Each case
asserted through the public API:

Policy (decided 2026-08-08): **removal cancels, insertion does not.**

- **A row above the active one is removed** — the drag cancels. This is the case that would
  otherwise silently produce a wrong drop, and cancelling is what prevents it, so assert the
  cancel fires even though nothing the user was interacting with disappeared.
- **The current `over` row is removed** — cancels; the item returns to its origin and
  `onDragEnd` never fires, so no landing position is reported against a list that moved.
- **The active row is removed** — cancels, the overlay unmounts, pointer capture is released
  (so the trailing `pointerup` lands nowhere harmful), and the announcement fires.
- **All three report `onDragCancel` with reason `'item-removed'`**, distinguishable from a
  user's Escape (`'escape'`) and from blur.
- **A row is *inserted* mid-drag** (lazy load resolving, or tree auto-expand-on-hover) — the
  drag **survives**: rects re-measure, `over` stays honest, no cancel. Assert this explicitly,
  because the symmetric-but-wrong implementation (cancel on any registry change) breaks the
  tree's own auto-expand.
- **A branch *collapses* mid-drag** — rows unmount, which is a removal, which **cancels, by
  design** (§ A7 F8). Assert the cancel fires with reason `'item-removed'`. This is the test
  that documents why the auto-expand recipe defers collapse restoration to
  `onDragEnd`/`onDragCancel` — restoring mid-drag is indistinguishable from a collaborator
  deleting the rows.
- **Removal during a keyboard drag** — cancels identically; focus returns to the handle and
  the announcement explains why, since a screen-reader user has no other way to learn the
  drag ended.

## Where it stands

`src/edge-cases.test.tsx` on disk (2026-08-08); 13 tests green, every one inside
`<StrictMode>` and driven through the public API. `bun run verify` clean.

It found two real defects, neither of which any earlier test could have caught.

### 1. Under StrictMode, a component mounting mid-drag cancelled the drag

The insertion case — "survives a row being inserted; lazy loads and auto-expand depend on it" —
failed. StrictMode runs a newly mounted component's effects **and its refs** as
attach → detach → attach, and mid-drag that middle detach is indistinguishable from a removal.
Under the A6 policy it cancelled. In the environment the demo runs in, tree auto-expand and
every lazily-loaded row would have cancelled the drag that caused them.

A first fix — skip unregistration when the element is still in the document — does not work:
React 19 detaches the ref during the simulated unmount too, so `nodeRef.current` is already
`null` when the cleanup runs. Confirmed by tracing the actual call, not assumed.

**The removal policy is now confirmed at the end of the current task**, not the instant a
registry entry goes: a removed id goes into a pending set, and a microtask later the store
cancels only for the ids that are *still* absent. A registration that came straight back was
never gone. That also covers the other case with the same shape — a consumer's inline
`ref={(node) => …}` being re-attached on every render.

The cost is that the cancel is now asynchronous, which thirteen tests had to be taught. They
`await flushRemovalCheck()` (new in `test/helpers.ts`) or `await act(async () => {})`, and the
helper's doc says why so the next person does not read it as a timing hack.

### 2. Nothing was listening for scroll

The scroll case was passing **vacuously** — the fixture's "near" target was a plain `<div>`
with a mocked rect and no `useDroppable`, so `over` never had anywhere else to be. Rewritten
properly, it failed: `DndProvider` had no scroll or resize listener at all, so a page moving
under a stationary pointer left the drop resolving against pre-scroll geometry.

`DndProvider` now attaches a **capture-phase** `scroll` listener (so scrolling in any container
is heard, not only the window's) and a `resize` listener for the duration of each drag, both
passive, both calling `store.markRectsDirty()`. The test moves a target's rect and fires a
scroll without touching the pointer, and asserts `over` follows.

### The rest

Disabled draggable keeps `role="button"` and `aria-disabled` and refuses **both** sensors;
disabled droppable never wins collision however near it is; Escape resets the transform and
fires no end; a second pointer changes nothing; the provider unmounting mid-drag leaves the
global listener count exactly where it started. All four A6 removal cases report
`'item-removed'`, the announcement says the list changed rather than claiming the user
cancelled, and the keyboard path cancels and explains identically.
