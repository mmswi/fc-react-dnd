# T9.1 — Integration: the full pointer flow

**Phase** P9 — Integration & verification · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

One test that walks a whole pointer drag through the real public API — provider, sensor,
store, collision, callbacks — and asserts what a consumer would actually observe. Unit
tests prove each piece; this proves they compose.

## Acceptance criteria

- Drives real DOM events (`fireEvent.pointerDown` / `pointerMove` / `pointerUp`), never
  sensor or store internals.
- Covers: press below the activation threshold (nothing happens) → cross the threshold
  (`onDragStart`) → move across two droppables (`onDragOver` fires on change only) →
  release (`onDragEnd`).
- **Callback order is asserted as a sequence**, not as a set of independent "was called"
  checks — order is the part that breaks silently.
- Payloads asserted: `active.id`, `active.data`, `over.id` (and `over === null` off-target),
  `translate`.
- Droppables positioned with `mockElementRect` from [T1.5](T1.5-test-harness.md).
- Runs inside `<StrictMode>`.

### It found a real gap in the event contract

The first version expected `['start', 'over', 'over', 'end']` and got three events. A drag very
often begins **already over** something — a card nearest a column, a sortable row over itself —
and nothing reported that: `onDragStart` carried only `active`, and `onDragOver` fired on
*changes*, so a consumer treating `onDragOver` as the single source of "current target" started
blind and stayed one target behind for the whole drag.

Fixed by adding `over` to **`DragStartEvent`**. The first attempt instead emitted an
`onDragOver` immediately after `onDragStart` — which worked for the events and broke
accessibility: the target announcement overwrote "Picked up X" before a screen reader could
speak it, and four announcement tests caught it. One event carrying complete information beats
two events racing each other.

The corrected sequence for a drag across two columns is `['start', 'over', 'end']`, and there is
a separate test that `start.over.id` is the column the drag began on.
