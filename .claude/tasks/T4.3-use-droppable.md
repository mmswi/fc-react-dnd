# T4.3 — `src/use-droppable.ts`

**Phase** P4 — React API · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Turn any element into a drop target: a ref to register the node, and `isOver`.

## Test first

Red tests before implementation:

- **`isOver` granularity.** Dragging across a list of droppables re-renders only the two
  whose `isOver` actually flipped — not every droppable, and not on every move within the
  same target (perf invariant 4).
- Registration in an effect, no notification, unregistered on unmount, StrictMode-clean
  (perf invariants 5, 8).
- `data` passes through to the `over` payload in drag events unchanged.
- A disabled droppable is never selected by collision — asserted through the public API,
  not by reaching into the store.
- A droppable that mounts **during** a drag is measured and becomes targetable, and one that
  unmounts mid-drag clears `over` rather than leaving a dangling id — both through the
  rect-dirty path, which is the perf-invariant-5 carve-out rather than an exception to it.
  This is not just a mount-order curiosity: it is the mechanism that keeps a **concurrent
  edit** correct (a collaborator deleting a row, a lazy load resolving). The geometry
  consequence matters more than the registry one — a removed row shifts every rect below it,
  so `over` must be recomputed against **re-measured** rects, not merely filtered for dead
  ids. See [`ANALYSIS.md`](../ANALYSIS.md) § A6.

## Acceptance criteria

- Exports `useDroppable`, `UseDroppableOptions`, `UseDroppableResult`; subpath
  `fc-react-dnd/use-droppable`.
- `disabled` supported and honoured by the store's collision args.
- No DOM measurement in the hook.
- `'use client'` at the top.
