# T4.3 — `src/use-droppable.ts`

**Phase** P4 — React API · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Turn any element into a drop target: a ref to register the node, and `isOver`.

## Test first

Red tests before implementation:

- **`isOver` granularity.** Dragging across a list of droppables re-renders only the two
  whose `isOver` actually flipped — not every droppable, and not on every move within the
  same target (perf invariant 4).
- Registration in an effect, no notification, unregistered on unmount, StrictMode-clean
  (perf invariants 5, 8).
- `data` passes through to the `over` payload in drag events unchanged.
- A disabled droppable is never selected by collision — asserted through the public API,
  not by reaching into the store.
- A droppable that mounts **during** a drag is measured and becomes targetable, and one that
  unmounts mid-drag clears `over` rather than leaving a dangling id — both through the
  rect-dirty path, which is the perf-invariant-5 carve-out rather than an exception to it.
  This is not just a mount-order curiosity: it is the mechanism that keeps a **concurrent
  edit** correct (a collaborator deleting a row, a lazy load resolving). The geometry
  consequence matters more than the registry one — a removed row shifts every rect below it,
  so `over` must be recomputed against **re-measured** rects, not merely filtered for dead
  ids. See [`ANALYSIS.md`](../ANALYSIS.md) § A6.

## Where it stands

`src/use-droppable.ts` + tests on disk (2026-08-08); 12 tests green, subpath `./use-droppable`
added, `bun run verify` clean. Registration follows the same ref-carries-the-node /
effect-owns-the-lifetime split as [T4.2](T4.2-use-draggable.md).

`isOver` is `state.overId === id` — a comparison against an **id**, which is why fifteen moves
inside one target re-render nothing at all. Asserted directly, alongside the exact-count
crossing test (two droppables flip, the third does not move).

### The store bug this task found: re-registering an unchanged node was treated as an arrival

The exact-count crossing test failed at 5 renders instead of 4, and the cause is general enough
to matter beyond this hook. A consumer's inline `ref={(node) => …}` is a new function every
render, so React re-attaches it on **every** render — including the per-move re-renders during
a drag. `registerDroppable` was treating each of those as a structural arrival: full re-measure,
re-collide, notify. That put a complete rect re-measure inside the move path (perf invariant 1,
straightforwardly violated) and gave every droppable a second render per boundary crossing.

Fixed in the store: an arrival is only an arrival when the node or the kind actually changed.
Re-registering the same node under the same kind changes no geometry, so it notifies nobody.

### The A6 asymmetry, asserted from the geometry side

Two tests, because the registry consequence is the easy half and the geometry consequence is
the one that bites:

- **Insertion survives**: a lazily-loaded row mounts mid-drag, wins collision, and no cancel
  fires.
- **Insertion re-measures the rows that stayed**: the inserted row pushes an existing row out
  of reach, and `over` moves to the new one. A cache that merely gained a candidate — rather
  than being re-measured — would leave the old row winning.
- **Removal cancels** with reason `'item-removed'`, and `over` is null afterwards, which is
  how "clears `over` rather than leaving a dangling id" is satisfied under the A6 policy.

### A trap in the second of those tests, worth knowing before writing another like it

It first failed because the test component re-mocked its rect **inside its ref callback**. The
re-render re-attached the ref, which reset the rect to its original value before the store could
re-measure it. Any test that changes an element's geometry has to change it where the component
will actually re-render with the new value — through props/state — not by poking the node behind
React's back.
