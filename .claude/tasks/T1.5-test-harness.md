# T1.5 — `test/setup.ts` and `test/helpers.ts`

**Phase** P1 — Scaffold · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Make jsdom capable of hosting a drag-and-drop library. jsdom has no layout engine and
no `PointerEvent`, so without this harness every sensor test would be testing the
absence of browser features rather than the library. This is the file that makes
ground rule 2 (test-first) practical for the rest of the project.

## Test first

The harness is itself proven by tests — write a small `test/helpers.test.ts` that
asserts `mockElementRect` is readable back through `getBoundingClientRect()` and that
`nextFrame()` resolves under faked rAF. A helper nobody tests is a helper that silently
lies to forty other tests.

## Acceptance criteria

`test/setup.ts`:

- Polyfills `PointerEvent` (carrying `pointerId`, `pointerType`, `clientX/Y`, `button`,
  `isPrimary`) so `fireEvent.pointerDown` produces something the sensors can read.
- Polyfills `setPointerCapture` / `releasePointerCapture` / `hasPointerCapture` on
  `Element` — jsdom has none of them, and the pointer sensor calls them.
- Stubs `Element.prototype.scrollIntoView` — jsdom lacks it too, and
  [T5.2](T5.2-keyboard-sensor.md) calls it on every keyboard target change. Missing this
  surfaces as a confusing "not a function" from inside the sensor.
- Every polyfill is applied **conditionally** (`if (typeof … === 'undefined')`), so the
  suite uses the real implementation wherever one exists and these never mask a genuine
  regression in a future jsdom.
- Registers any global cleanup the suite needs between tests.

`test/helpers.ts`:

- `mockElementRect(el, rect)` — makes `getBoundingClientRect()` (and the offset/client
  properties the store reads) return the given rect, so droppables can be positioned in
  a test with no layout engine.
- `nextFrame()` — advances one animation frame under
  `vi.useFakeTimers({ toFake: ['requestAnimationFrame'] })`, for the rAF-coalesced
  overlay writes and the auto-scroll loop.
- Both are typed; no `any`.

## Where it stands

`test/setup.ts`, `test/helpers.ts`, and `test/helpers.test.ts` on disk (2026-08-08); nine
tests green. Written test-first, and the red steps were observed rather than assumed: the
first run failed with *"Cannot find module test/setup.ts"* (the config pointing at a file
that must exist), the second with the missing `./helpers.js`, the third passed.

Decisions a later reader will want the reasoning for:

- **Pointer capture is a real set, not a no-op.** `setPointerCapture` records the id and
  `hasPointerCapture` reads it back through a `WeakMap<Element, Set<number>>`. Stubbing the
  three methods as empty functions would let a test that asserts capture pass whether or not
  the sensor ever called it.
- **`test/helpers.ts` owns `ElementRect` rather than importing the library's `Rect`.** It is
  the input to a jsdom stub, and the four numbers a test author types are top/left/width/height
  — right and bottom are derived in one place so no test can state them inconsistently. The
  harness also stays unaffected by a library type change mid-refactor.
- **`nextFrame()` advances exactly one frame** (`vi.advanceTimersToNextFrame()` plus a
  microtask yield), so a self-rescheduling rAF loop — the overlay's write loop, auto-scroll —
  can be stepped one frame at a time instead of spinning. There is a test for precisely that.
- **`cleanup()` from `@testing-library/react` runs in a global `afterEach`.** RTL's automatic
  cleanup depends on test globals, which `"types": []` deliberately denies us, so it is
  registered by hand once here instead of leaking DOM across forty test files.
