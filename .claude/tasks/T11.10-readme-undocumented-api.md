# T11.10 — The README documents a subset of what ships

**Phase** P11 — Defects found after v0.1 · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

Found 2026-08-12 by auditing the README against `package.json#exports` and the source, after the
user asked what was missing from it. The API *table* was exactly accurate — every subpath, every
export, no drift — so the gap was not in the surface it lists but in the surface it explains.

`README.md` is the npm landing page: `npm pack --dry-run` puts it in the tarball regardless of
`files: ["dist"]`, so it is the only documentation a consumer sees before installing.

## The red test

Not a unit test — the failure mode is documentation, not behaviour. The check that stands in for
one, and the reason the examples can be trusted: **every `tsx` block in the README is extracted to
a temp directory inside the repo and compiled**. That is release-checklist item 2 ("README examples
compile against the current API") made executable rather than asserted.

**What it actually resolves against, corrected 2026-08-12:** the harness was written with
`paths: { "fc-react-dnd/*": ["../src/*"] }` and described as compiling against `src/`. It does not.
Because the temp directory sits inside the package, TypeScript resolves `fc-react-dnd/<subpath>`
through the package's **own `exports` map** — Node's self-referencing rule — so the examples
compile against the built `dist/`. Discovered when [T11.11](T11.11-apply-sort-end.md) added
`fc-react-dnd/list` and the harness failed with `Cannot find module` while `src/list.ts` existed
and its tests passed: `dist/list.d.ts` had not been built yet.

Keep it that way — checking the README against the *published* types is the stronger check, since
that is what a consumer gets. The consequence to remember: **run `bun run build` before the harness**,
or a newly added subpath reads as a broken example.

## The Quickstart taught a no-op memo (user, 2026-08-12)

Caught by the user reading the finished Quickstart:

```tsx
const itemIds = useMemo(() => items, [items])   // returns the array it was given
<SortableList items={itemIds}>
```

The factory returns `items`, so `itemIds` **is** `items` — identical reference, no memo. It was
worse than nothing: `items` from `useState` is already stable until `setItems` replaces it, and the
comment above the line claimed the memo bought that stability, so the one example most readers copy
taught a cargo cult. The Quickstart now passes `items` directly.

Underneath it was the question the README never answered: **`SortableList` wants ids, and most
state holds objects.** The naive `items.map((item) => item.id)` inline is exactly the ✗ case in
contract 1 — a new array every render, so the projection memo misses on every notification and the
move path goes quadratic. Contract 1 now shows the derivation with the memo that is real
(`useMemo(() => tasks.map((task) => task.id), [tasks])`), names the no-op form as the thing it is
not, and notes that `useTreeDrop` has no equivalent trap because it takes the objects themselves.
