# T11.4 — the server story, tested instead of asserted

**Phase** P11 · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Two claims this repo makes in prose and never ran:

1. **It renders on a server.** `CLAUDE.md` and `store.ts`'s header both say the store is built
   per `DndProvider` so it is SSR-safe. Every suite ran under jsdom, where `document` exists —
   so the one environment that could catch a module-scope DOM touch was the one never used.
2. **It hydrates without a mismatch.** Rendering on the server only proves the server half.
   `DndProvider` calls `useId` for `instructionsId` and every handle's `aria-describedby` points
   at it, so a tree that differs by one node across the boundary re-keys the id and silently
   breaks the a11y wiring — with the markup still looking right.

Opened by the user (2026-08-09), asking what happens to the store on the server and then:

> Want me to add a hydrateRoot test that asserts no mismatch warnings? YES

## The test that opens it

`src/hydration.test.tsx`, under the default jsdom environment — `hydrateRoot` needs a DOM, so it
cannot live in `ssr.test.tsx` (`@vitest-environment node`).

The **red** step is the deliberate-mismatch case: hydrate a client tree that differs from the
server HTML and assert the harness reports it. Written the other way round, a test that collects
zero errors because the detection never fired is indistinguishable from a passing one — the
failure mode this session has already hit four times.

## Acceptance criteria

- Server-renders and hydrates a sortable list and a tree; no `onRecoverableError`, no
  `console.error`.
- The `useId`-derived `aria-describedby` resolves to a real element **after** hydration, so the
  test pins the a11y wiring and not merely the absence of a warning.
- A deliberately divergent client tree fails the same assertions — committed as its own test, not
  a manual check.
- Hydration is wrapped in `act` so registration effects and monitor subscriptions actually run;
  otherwise the assertions read a half-committed tree.
- Both channels are collected (`onRecoverableError` **and** `console.error`), because which one
  React 19 uses for a given mismatch is not worth guessing.

## Where it stands

**Server half: done**, commit `b9911ec` — `src/ssr.test.tsx`, 6 tests. It needed a `hasDom` guard
in `test/setup.ts`: setup files run in the node environment too, and
`class PointerEventPolyfill extends MouseEvent` threw at module scope before the suite could
execute a line. That guard is why an SSR suite was impossible to write before.

**Hydration half: done** — `src/hydration.test.tsx`, 5 tests. Suite total 455 → **510**.

Which channel reports a mismatch, now known rather than guessed: React 19 sends the entire diff
to `onRecoverableError` and writes **nothing** to the console, because supplying a handler
replaces the default and the default is the one that logs. Both are still collected — the console
array is what would catch a key warning or an act violation.

### The store-on-the-server question, and why nothing changed

The user asked for the store to be `null` on the server, to avoid a memory leak. Measured
instead of argued (`ANALYSIS.md` § A12): one store is **~973 bytes**, and **5000 server renders
retain nothing** — the post-GC heap delta comes out negative. There is no leak, so the premise
for the change does not hold and the code was left alone.

If it is ever reopened, the shape to build is one **frozen, inert** store shared by every server
render — not a nullable `store` in the context, which puts a null branch in every hook forever.
And the reason to hesitate is not the branch: a second `DragStore` implementation is a
hydration-mismatch generator. TypeScript enforces the stub's *shape*; nothing enforces that its
`getState()` agrees with the real store's initial state, so the next field added to
`DragStoreState` diverges the two silently.
