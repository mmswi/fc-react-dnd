# T8.4 — The projection carries its own indicator anchor

## Goal

Add `indicator: { rowId, edge, depth }` to `TreeDropProjection`: the **screen-space** anchor an
indicator is drawn against, resolved by the library instead of re-derived by every consumer.

API addition, so it is its own task per the public-API policy. Opened by the user's screenshots
(2026-08-08): "the into styling is not triggered always", "some confusing ui", "it says
between, but goes into".

## The test that opens it

`src/tree.test.ts` — six red tests, the sharpest being the one the screenshots showed:

```ts
it('puts the into box on the parent row itself, not its first child', () => {
  const projection = project({ pointerY: centreOfRow(1) })

  expect(projection?.mode).toBe('into')
  expect(projection?.indicator).toEqual({ rowId: 'guide', edge: 'over', depth: 1 })
})
```

## Acceptance criteria

- `into` anchors on the target row at the target row's own indent — never on its first child.
- A plain gap anchors below the row above it; the top gap anchors above the first row.
- "First child via the gap" anchors directly **below** the parent row.
- An un-nest anchors below the **last visible row of the subtree** it lands after.
- `treeProjectionsAreEqual` compares the indicator, so the equality that guards renders cannot
  lie about it.
- The playground consumes `projection.indicator` and derives nothing itself.
- `bun run verify` green.

## Where it stands

Done. 468 tests, `verify` green.

**Why the library owns this now.** `afterId`/`beforeId` are sibling-space; drawing needs
screen-space; and the demo — written with full knowledge of the projection's semantics — got
the translation wrong three separate times:

1. The anchor chain `afterId ?? beforeId ?? parentId` sent an `into` box to the target's
   **first child**, because `into` sets `beforeId` to that child for `applyTreeDrop`'s benefit.
   Visible in the screenshots as "into styling is not triggered always": it triggered, one row
   too low, precisely when the target had children.
2. The same chain drew "first child via the gap" (`afterId: null`, `beforeId` often `null`) in
   the gap **above** the parent — a different gap entirely: "it says between, but goes into".
3. An un-nest drew immediately below the ancestor's own row instead of below its subtree
   (fixed in T8.3, in the demo — the walk now lives in the library).

Three failures by the best-placed consumer is the argument: every other consumer would fare
worse. The projection computes the anchor from data it already holds (`positioned`, the
ancestor walk), so the cost is one subtree scan per projection change, memoised per store
version like everything else.

**Also this session, same screenshots:**

- A test pinning the user's exact gesture: the **last child** of a parent dropped into the
  sibling above it works (`usage` → into `install`). In the demo it looked broken because the
  row it was tried against was `on-call` — the demo's one deliberately locked node. The demo
  now renders a 🔒 on that row so the policy is visible instead of reading as flakiness.
- The ghost names the landing parent on **every** nesting drop ("↳ into Onboarding"), not only
  in the middle-band case — both `into` and first-child-via-gap are drops into a parent, and
  labelling only one of them made the other look like a contradiction. At the root it says
  "top level".
- The demo passes `nestBandFraction: 0.25` (library default 0.3): 34px rows leave a 13.6px
  middle band at the default, which made `into` feel hard to hit.
