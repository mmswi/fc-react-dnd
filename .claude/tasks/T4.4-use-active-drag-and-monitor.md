# T4.4 — `src/use-active-drag.ts` + `src/use-dnd-monitor.ts`

**Phase** P4 — React API · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Two ways to observe a drag from anywhere in the subtree: `useActiveDrag` for components
that want to *render* from the active drag, and `useDndMonitor` for components that want
to *react* to it without re-rendering at all.

## Test first

Red tests before implementation:

- `useActiveDrag` re-renders on start and end, and **not** per move — unless the consumer
  selects something that changes per move. Render counter asserts it.
- `useDndMonitor` causes **zero** re-renders in its host component while firing on every
  event — that's the entire point of it existing alongside `useActiveDrag`.
- Listeners are read through a latest-ref, so passing new inline closures each render
  does not resubscribe on every render.
- Unsubscribes on unmount; StrictMode leaves exactly one subscription.
- Both throw the named out-of-provider error from [T3.3](T3.3-context.md).

## Acceptance criteria

- `useActiveDrag` exported at `fc-react-dnd/use-active-drag`.
- `useDndMonitor` + `DndMonitorListeners` exported at `fc-react-dnd/use-dnd-monitor`,
  covering start / move / over / end / cancel.
- Monitor listeners fire **before** state reset on end/cancel, matching
  [T3.1](T3.1-store.md) — a listener reading the drag during `onDragEnd` sees it.
- `'use client'` at the top of both.

### `useActiveDrag` takes no selector, and returns the store's `origin` directly

The criteria say it re-renders on start and end "unless the consumer selects something that
changes per move". That clause is served by the *other* two mechanisms rather than by a
selector parameter here: `DragOverlay` moves with no React render at all, and `useDraggable`'s
`trackTransform` is the opt-in for a source element that follows the pointer. A selector
parameter would have needed its own snapshot object, which is a fresh reference per call —
i.e. the uncached-`getSnapshot` infinite loop, deliberately not built.

So it returns `state.origin`, whose identity survives every move by construction
([T3.1](T3.1-store.md)). Two tests pin that: exact render counts across a 20-move drag, and
the identity itself (`read()` before and after a move is `toBe`-identical). The second is
what *explains* the first, so it stays even though the first would catch a regression.

The public type is **`ActiveDragInfo`** in `src/types.ts` — `{ id, data, rect }`, where `rect`
is where the item started. The internal `DragOrigin` is now defined as
`ActiveDragInfo & { pointer }`, so the shared half has one definition rather than two that
drift. Note the naming: `ActiveDragInfo` and `DragActive` are different things —
`DragActive` is the event payload and carries the *translated* rect. They are not the same
concept with the words swapped, and the doc comments on both say which is which.

### `useDndMonitor`'s latest-ref test counts subscriptions, not renders

Passing fresh inline closures every render must not resubscribe, and a resubscribe is
invisible from the outside until it drops an event or leaks. The test forces two parent
re-renders with new closures, then starts a drag, and asserts the listener fired **exactly
once** carrying the value from the **latest** closure. One call proves one subscription; the
value proves the ref is current.
