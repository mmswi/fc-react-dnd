# T3.1 — `src/internal/store.ts`

**Phase** P3 — Store & subscription layer · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

The heart of the library: a plain external store holding all drag state, created **per
`DndProvider` instance** — never module-level, so it is SSR-safe and multi-provider-safe.
This is where the central performance claim is either true or false: rects are measured
once at drag start and every subsequent move is pure arithmetic against the cache.

## Test first

The store is synchronous by design and needs no React and no frame control, so it can be
driven directly. Red tests before implementation, one behaviour at a time:

- **Registration never notifies — while idle.** Subscribe, register and unregister a
  draggable and a droppable with no drag active, assert the subscriber was called zero times
  (perf invariant 5).
- **But registration during a drag is a structural event, and the policy is asymmetric**
  (decided 2026-08-08, [`ANALYSIS.md`](../ANALYSIS.md) § A6):
  - **Unregistration cancels.** Unregister *any* droppable or draggable mid-drag — the active
    one, the current `over`, or an unrelated row above it — and assert the drag cancels via
    the cancel path (not the end path), transforms reset, `onDragEnd` does **not** fire, and
    teardown is complete. The unrelated-row case matters most: it is the one that would
    otherwise resolve silently against a stale rect cache and produce a wrong drop with no
    error anywhere.
  - **Registration does not cancel.** Mount a droppable mid-drag and assert rects are marked
    dirty, re-measured, and collision re-runs — with the drag still alive. Cancelling here
    would break tree auto-expand-on-hover and lazy-loading lists.
- The cancel path must carry **why** it fired, so `onDragCancel` can distinguish a user's
  Escape from a forced cancel (see [T4.1](T4.1-dnd-provider.md)).
- **Rects measured once.** Count measurement calls across `beginDrag` + N `updateDrag`
  calls; assert measurement happened once, not N+1 times (perf invariant 1).
- **Dirty flag.** After a scroll/resize signal, the next update re-measures — and only
  the next one.
- **Stale session token.** A `DragSession` captured before `endDrag` becomes a no-op
  afterwards: calling `move` / `setTransform` / `end` on it changes nothing and notifies
  nobody.
- **Events fire before state reset.** An `onDragEnd` listener reading active/over during
  the callback sees the drag that just ended, not a cleared state. Same for cancel.
- **Monitor fan-out** reaches every listener; unsubscribing one leaves the others intact.
- **Immutable state object** — every notifying transition produces a new state reference,
  which is what makes the WeakMap memoization in [T7.1](T7.1-list-projection.md) and
  [T8.2](T8.2-use-tree-drop.md) sound.

## Acceptance criteria

- A factory function, not a class (per the standards).
- Registries for draggables and droppables; register/unregister mutate without notifying.
- **A third registration kind: measure-only** (§ A7 D3/F7 in [`ANALYSIS.md`](../ANALYSIS.md)).
  Tree rows register rects for the cache and for keyboard targeting but are **excluded from
  collision** — `closestCenter` never sees them, and they never produce `over`. Internal
  only (reached through `useTreeDrop`'s `getRowProps`, not `useDroppable`). They still count
  as registered nodes for the A6 removal-cancels policy.
- **The mid-drag structural path mints a new state version even when `over` is unchanged**
  (§ A7 F6): an insertion re-measures and re-collides, and *must* produce a new state object
  so per-drag derived projections recompute — subscribers whose slices are unchanged still
  don't render (A3.1 gate 1), so this is cheap. Assert: register a droppable mid-drag with
  `over` unchanged, and the state object identity still changes.
- Lifecycle: `beginDrag`, `updateDrag`, `endDrag`, `cancelDrag`.
- `DragSession` handed to sensors on activation, guarded by a session token so a stale
  session cannot resurrect a finished drag.
- Droppable-rect cache: batched reads at `beginDrag`, re-measured lazily via the dirty
  flag — **no DOM reads in the move path** (perf invariant 1, 2).
- Collision runs against the cache on every move, with disabled droppables filtered here
  (the boundary [T2.3](T2.3-collision-closest-center.md) deliberately leaves to the caller).
- Complete teardown on end/cancel — no per-interaction state survives (perf invariant 7).
- Named constants for any tunable; no `any`.
- **Know the tearing-recovery cost before designing the notify path.** Mutating an external
  store during a concurrent render makes React discard it and re-render the whole tree
  *synchronously* — `renderRootSync`, with the comment *"A store was mutated in an
  interleaved event. Render again, synchronously, to block further mutations"*
  (`ReactFiberWorkLoop.js:1151-1173`). This library mutates the store on every pointermove,
  which is exactly that case. Mitigating detail: the check is skipped for blocking lanes
  (`ReactFiberHooks.js:1691`) and recovery runs only `if (renderWasConcurrent)`, so
  discrete-input drags aren't exposed — a concurrent render in flight elsewhere in the app
  is. See [`ANALYSIS.md`](../ANALYSIS.md) § A3.3, which also proposes measuring it.

### The state shape, and the one decision the whole architecture rests on

```ts
type DragStoreState = {
  origin: DragOrigin | null                      // id, data, rect, pointer — stable per drag
  overId: DndId | null                           // an id, not an object
  translate: Translate                           // the only thing that changes per move
  measuredRects: ReadonlyMap<DndId, Rect>        // replaced, never mutated (A9.3)
}
```

**`origin` is split from `translate` deliberately, and it is not cosmetic.** A single `active`
object carrying the translated rect would get a new identity on every pointermove, so
`useActiveDrag` — and anything else selecting it — would re-render at pointer frequency and
perf invariant 4 would be false in practice while still being true on paper. The moving part
lives in `translate`; the stable part is `origin`, and a test asserts its identity survives a
drag. Likewise `overId` is an *id*, not a `DragOver` object: within one target, many moves
change nothing a droppable would re-render for.

The public `DragActive` (with the translated `rect`) is **derived** when an event is built, so
consumers still get the convenient shape without it costing a render per move.

`origin.data` is a **snapshot** taken at `beginDrag`, not a live read of the registry. A drag
reports the item as it was picked up, and a consumer changing `data` mid-drag does not
retroactively rewrite the event they are about to receive.

### `markRectsDirty` both marks and immediately updates, which reconciles two criteria

The criteria ask for a lazy dirty flag ("the next update re-measures — and only the next one")
*and* for `over` to update on scroll with a stationary pointer ([T9.3](T9.3-edge-cases.md)) —
lazily alone cannot do the second. Resolved by having `markRectsDirty` set the flag and then
run one update cycle immediately: that cycle re-measures and clears the flag, so a subsequent
pointermove does not measure again. Both criteria hold, and both are asserted by counting
calls through the injected `readRect`.

That update cycle reports `onDragOver` if the target changed but **not** `onDragMove` — a
scroll is not a move, and emitting one would make consumers see phantom pointer motion.

### `src/internal/dom.ts` — one function, and that is the point

`readElementRect` is the library's only DOM read. The seam exists so the store can be handed a
counting substitute, which is what makes perf invariant 1 an assertion rather than a claim:
the tests count measurement calls across `beginDrag` + 20 moves and require the total to be
unchanged from the count at start.

### Two additions to the store's API beyond the criteria

- **`cancelActiveDrag(reason)`** — the removal path needs it internally, and
  [T4.1](T4.1-dnd-provider.md)/[T9.3](T9.3-edge-cases.md) need a provider unmounting mid-drag
  to tear down without going through a sensor's session.
- **`setCollisionDetection`** — `DndProvider`'s `collisionDetection` prop can change between
  renders, and the store must not be recreated for it. The store deliberately does **not**
  import `src/collision.ts`; the default lives in the provider, so `internal/` never depends
  on a public module for behaviour.

### `DndMonitorListeners` lives in `src/types.ts`, not in `use-dnd-monitor.ts`

`CLAUDE.md`'s module map put it on the hook. The store fans events out to these listeners, so
defining it in the hook would make the internal store import a public React module just to
describe its own contract — or force a re-export hub, which ground rule 4 forbids. The hook
exports `useDndMonitor`; the type is shared vocabulary and lives with the rest of it.
`CLAUDE.md`'s module map is corrected in the same commit.

## Amended 2026-08-08 — rects were measured through the consumer's own animation

The user reported the sortable "works, then stops working": the second drag of a session
displaced the wrong rows entirely — a row *above* the dragged one moving 205px while the rows
below it stayed put.

`readElementRect` used `getBoundingClientRect()`, which reports the **visual** box, transform
included. This library asks consumers to animate rows with `transform` (perf invariant 3), so a
drag begun while the previous drop's 200 ms transition was still running measured every row
mid-flight and built the whole projection on geometry that was about to stop being true.

The library was, in effect, reading its own output back in as input.

`internal/dom.ts` now subtracts the element's own translation, giving the layout position the
transform is measured *from*. `translationOfTransform` handles both `matrix()`/`matrix3d()` — what
a browser computes to — and the `translate…()` shorthands, which is what **jsdom** returns; handling
only the matrix forms would have made the correction silently do nothing in the environment
everything else is tested in.

Pinned by `src/sortable.consecutive-drags.test.tsx`, whose rows carry a leftover transform *and*
report a rect that includes it, exactly as a browser does. Confirmed to fail without the fix:
without it the drag moves row `a` instead of row `b`.

That file is also the answer to a gap this project had all along — **every sortable test until now
dragged exactly once.** The failure needed a second drag, and nothing was looking.
