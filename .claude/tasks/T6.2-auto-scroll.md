# T6.2 — `src/internal/auto-scroll.ts`

**Phase** P6 — Overlay, auto-scroll, accessibility · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Scroll the container when the pointer nears its edge, without turning the move path into a
layout-thrashing loop. The trick is separating the decision from the effect: a pure
`computeScrollIntent` that is exhaustively testable, and a thin rAF loop that applies it.

## Test first

Red tests before implementation:

- `computeScrollIntent` is **pure** and table-driven: pointer well inside the container →
  no intent; near an edge → intent on that axis; in a corner → both axes; speed ramps with
  proximity; a container already scrolled to its end yields no intent on that axis (no
  pointless loop spinning).
- Scrollable-ancestor discovery picks the nearest genuinely scrollable ancestor, skipping
  `overflow: visible` ones, and falls back to the viewport.
- The rAF loop runs only during pointer drags, and **not** during keyboard drags (the
  keyboard path uses `scrollIntoView` instead — [T5.2](T5.2-keyboard-sensor.md)).
- Each scroll tick marks rects dirty and re-collides, so `over` stays correct as content
  moves under a stationary pointer. This is the bug that makes naive autoscroll feel
  broken; it gets its own test.
- The loop stops and is cancelled on end, cancel, and unmount — nothing survives the drag
  (perf invariant 7).

## Acceptance criteria

- `computeScrollIntent` is exported from the internal module, pure, and DOM-free.
- Reads batched before writes; no interleaved read/write in the loop (perf invariant 2 —
  see the `layout-thrashing-prevention` skill).
- Every threshold is a named constant (`AUTO_SCROLL_EDGE_PX`, max speed, …).
- Enabled/disabled through `DndProvider`'s `autoScroll` prop.

### The decision is pure; the loop is thin

`computeScrollIntent({ pointer, box })` takes a `ScrollBoxMetrics` — rect, scroll offsets,
scroll extents, client extents — and returns a per-axis speed. No DOM, so all eleven of its
cases are table-driven: inside, each edge, the corner, the ramp, the exact band boundary, both
"already at the end" cases, one axis blocked while the other moves, and the pointer outside the
box entirely.

The loop reads all metrics in one batch, decides, then writes — never interleaving (perf
invariant 2). And **every scrolling tick calls `store.markRectsDirty()`**, which is the step
naive autoscroll skips and the reason a drop lands one row off after a scroll. Its test moves a
droppable out of reach *during* the scroll and asserts `over` follows.

### Keyboard drags never enter the loop, by construction

`start()` refuses when `origin.pointer` is null, so a keyboard drag cannot auto-scroll — it
uses `scrollIntoView` ([T5.2](T5.2-keyboard-sensor.md)). That is A9.2's nullable pointer
paying off: no `activatorType` enum for a future sensor to classify itself into wrongly.

`store.getActiveNode()` was added so the scroller can resolve the scroll container from the
element the drag started on.

### Two jsdom gaps found, both fixed in a way that is also right in a browser

- **`getComputedStyle` does not expand the `overflow` shorthand.** With `style.overflow =
  'auto'`, jsdom reports `overflow: "auto"` and leaves `overflowX`/`overflowY` empty. Checking
  longhands alone finds nothing under test; checking the shorthand alone misses a consumer who
  set `overflow-y` directly. Reading all three is correct in both environments.
- **`document.scrollingElement` is `undefined` in jsdom.** The viewport fallback is now
  `document.scrollingElement ?? document.documentElement`.

Both were caught by tests failing, not by reading docs — the first draft returned `undefined`
for every lookup, and the "falls back to the viewport" test passed anyway because it compared
`undefined` to `undefined`. Recorded because it is the shape of a vacuous test: an assertion
whose expected value is computed the same wrong way as the received one.
