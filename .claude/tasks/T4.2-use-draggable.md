# T4.2 — `src/use-draggable.ts`

**Phase** P4 — React API · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Turn any element into a drag source: a ref to register the node, `handleProps` to spread
on the handle, and the two pieces of state a consumer actually renders from — `isDragging`
and `transform`.

## Test first

Red tests before implementation:

- **Selector granularity.** A draggable that reads only `isDragging` re-renders on drag
  start and end — and **not once per pointermove**. Render counter across a 20-move drag
  asserts the exact count (perf invariant 4). The inverse case: a draggable that *does*
  select `transform` re-renders per move, and only the active one does.
- Registration happens in an effect, notifies nobody, and unregisters on unmount; clean
  under StrictMode (perf invariants 5, 8).
- `handleProps` merges the activators of **all** configured sensors — adding a second
  sensor must not silently drop the first one's listeners.
- A consumer's own `onPointerDown` passed through `handleProps` still fires alongside the
  sensor's.
- Disabled: keeps `aria-disabled`, loses activation listeners, and a pointerdown starts
  nothing (accessibility invariant 4).

## Acceptance criteria

- Exports `useDraggable`, `UseDraggableOptions`, `UseDraggableResult`; subpath
  `fc-react-dnd/use-draggable`.
- `handleProps` carries `role="button"`, `tabIndex={0}`, `aria-roledescription`,
  `aria-describedby` → the instructions element, `touch-action: none`, and
  `draggable={false}` (accessibility invariant 3).
- `data` is `Record<string, unknown>` and reaches the drag events unchanged.
- No DOM measurement in the hook — rects are the store's job.
- `'use client'` at the top.

### Registration: the A8/A9.4 decision, corrected by what the tests found

A8 asked whoever built this to choose between ref-callback and effect registration and record
it. The answer turned out to be **both, split by responsibility**, because each alone cancels
drags — for opposite reasons:

- **The ref callback carries the node** and never unregisters.
- **An effect keyed on `[store, id]` owns the registration's lifetime**; its cleanup is the
  only thing that unregisters.

Effect-only registration fails on `data`: with `data` in the dependency array, an ordinary
`data={{ index }}` re-render mid-drag unregisters and re-registers, and under A6 that cancels
the drag. That was A9.4's argument and it stands.

**What A9.4 missed** is that unregistering from the ref *cleanup* is just as bad. A consumer
writing `ref={(node) => { myRef.current = node; setNodeRef(node) }}` hands React a new function
every render, so React detaches and re-attaches on every re-render — including the per-move
re-renders of the item currently being dragged. That detach is not a row disappearing, and
treating it as one cancels the drag on its **first pointermove**. Five tests failed on this
before the split; the test component deliberately still uses an inline ref wrapper so the
regression cannot come back unnoticed.

The effect also **re-registers on setup**, not only unregisters on cleanup, because StrictMode
runs setup → cleanup → setup: without it, that middle cleanup leaves a mounted draggable
permanently unregistered.

`registerDraggable` / `registerDroppable` now **carry `data` and `disabled` across a
re-registration**, so a node swap does not wipe options that the options effect has no changed
dependency to restore. Asserted by the node-swap test.

### `trackTransform`, and why it defaults to on

The criteria ask for two granularity behaviours — "reads only `isDragging`" re-renders twice
per drag, "selects `transform`" re-renders per move — but a hook that always returns
`transform` cannot express the first: the component re-renders whenever anything it is handed
changes, whether or not it reads it. So the subscription is an explicit option.

It defaults to **on**, because a draggable that does not move is a surprising default, and the
library's headline granularity numbers come from `useSortable`
([T7.4](T7.4-sortable-granularity-tests.md)) which reads its translate from the memoised list
projection and turns this off. Documented with its failure mode in the hook's TSDoc and in
[T10.1](T10.1-readme.md).

### `activatorProps`

The criterion "a consumer's own `onPointerDown` still fires alongside the sensor's" is
unachievable by spreading — `<div {...handleProps} onPointerDown={mine} />` is plain React
overwriting. So consumer handlers go **in**, as `options.activatorProps`, and are merged into
the same chain as every sensor's. Asserted alongside the two-sensor merge test.

### A general lesson for every render-count test in this repo

"Re-renders per move" first failed at 3 instead of 7 — because all five moves ran inside a
single `act()`, where React batches them into one render. **One `act()` per move**, since each
pointermove is its own discrete event in a browser. Batching moves into one act coalesces N
renders into 1 and passes a test that should fail.
