# T11.11 — `applySortEnd`: the list side never shipped its apply step

**Phase** P11 — Defects found after v0.1 · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

Opened by the user 2026-08-12, reading the README's `onSortEnd` example: *"why haven't we
introduced this logic into the actual library? seems like you pass responsibility to the consumer,
instead of making it plug and play."*

Checked before answering: **no decision on record anywhere** — not in `ANALYSIS.md`, not in the
Backlog, not in any task file. It was never considered, rather than considered and declined.

## The asymmetry

The library's thesis is that it returns the **outcome**, not the gesture. For trees it goes all
the way: `applyTreeDrop(items, activeId, projection)` hands back the new tree. For lists it stops
one step short — `SortEndEvent` carries `fromIndex`/`toIndex`/`afterId`/`beforeId` and the consumer
writes the splice.

Worse than a missing convenience: the README's *Concurrent edits* section says `afterId`/`beforeId`
exist **because indices are unsafe** when a collaborator edits mid-drag, and then every example
reordered by index. The safe fields shipped, using them meant hand-writing id resolution, so the
demonstrated path was the unsafe one.

Also undocumented: `toIndex` indexes the array **after** the active item is removed
(`sortable-list.tsx:82-90` builds the neighbours from `withoutActive[toIndex]`, pinned by
`sortable-list.test.tsx:88`). Remove-then-insert is correct; insert-then-remove is an off-by-one
that only shows on downward moves. Five lines of consumer code with load-bearing ordering nothing
stated.

## Shape, and what was rejected

Decided with the user: **a pure exported function, nothing added to the event.**

```ts
applySortEnd<Item>(items: readonly Item[], event: SortEndEvent, getId: (item: Item) => DndId)
```

- **Rejected — `SortableList` hands back a ready-made list.** The user proposed it; two things kill
  it. `SortableList` only ever sees `readonly DndId[]`, so the list it can build is of *ids*, and
  object-shaped state — the common case — would have to map ids back to objects through a lookup.
  And the obvious implementation reorders `projection.orderedIds`, which is **measured rows in
  visual order** (`list-projection.ts:72-77` skips ids with no rect, then sorts by position), so a
  virtualized list would lose every off-screen row on drop.
- **Rejected — a precomputed array on the event.** It is a drop-time snapshot taken from
  `latest.current.items`, refreshed at the last commit. `setTasks((current) => applySortEnd(current, …))`
  runs against whatever React has queued *now*, which is the whole point under A6.
- **`getId` is required, not defaulted.** An identity default would need `item as unknown as DndId`
  in its body — a double assertion that would let `Task[]` compile with the wrong getId and fail
  silently at runtime (ids never match, list returned unchanged). Explicit `(id) => id` for id
  arrays is the honest cost.
- **Module named `list.ts`, not `apply-sort-end.ts`**, mirroring `tree.ts` — the pure-domain-module
  pattern the repo already uses for the tree maths, and it reads as the counterpart it is:
  `applySortEnd` from `fc-react-dnd/list` beside `applyTreeDrop` from `fc-react-dnd/tree`.

## The red test

Four vertical slices, each red before green (`src/list.test.ts`):

1. moves the item between the neighbours it landed between → module did not exist
2. falls back to `beforeId` when the `after` neighbour is gone → landed at index 0 instead
3. falls back to the captured slot, clamped, when both are gone → landed at index 0 instead
4. hands back the same array reference when nothing moved → built a new array

Then the API pin: `src/public-api.test.ts` listed `./list` before `package.json` did, and failed on
the subpath-list comparison before the export map was added.

## Acceptance criteria

- `applySortEnd` resolves by id first and the captured index only as a last resort.
- Same array reference back when the drop changes nothing.
- Items that did not move keep their identity (no copying), so memoised rows bail out.
- Pure: no `'use client'`, importable from a server component, no React import.
- README's examples use it instead of a hand-written splice; `CHANGELOG.md` records the addition.
- `bun run verify` green.

## `readonly` in, `readonly` out — the one ergonomic cost

Found by the playground typecheck, not by review: `applySortEnd` returns `readonly Item[]`, so
`useState(['a', 'b'])` — which infers a mutable `string[]` — rejects the updater with TS2345.

Kept anyway, because `applyTreeDrop` already returns `readonly TreeItem<Extra>[]` and the tree page
already declares its initial constant `readonly`. One rule for both halves of the library beats a
list-shaped exception. The alternatives were worse: a generic
`<Items extends readonly unknown[]>(items: Items) => Items` preserves the caller's mutability but
needs an internal `as Items` on the rebuilt array, and returning a mutable `Item[]` cannot also
return the *input* array in the no-op path — which would cost the identity guarantee that lets a
memoised list bail out.

So the contract is: **declare the initial array `readonly` and let `useState` infer it**, exactly as
`tree-page.tsx:71` already does. Applied to `playground/src/sortable-page.tsx` (a new `Task` type on
`initialItems`), `playground/src/comparison-page.tsx` (`useState<readonly string[]>`), and the
README Quickstart.

## Where it stands

Done 2026-08-12. `src/list.ts` (one export, one private `resolveLandingIndex`, one private `clamp`)
and `src/list.test.ts` (5 tests). Published as `fc-react-dnd/list` in `package.json#exports` and
pinned in `public-api.test.ts`. Both README examples — the id-array Quickstart and the objects one —
now call it, and the *Server components* list gained the new subpath.

**Playground** (both pages that reordered by hand, at the user's request so the function can be
seen working): `sortable-page.tsx` now applies the drop with `applySortEnd(current, event, (item) => item.id)`
and prints the resulting id order under the `onSortEnd` payload, so the event and its effect are
visible side by side; `comparison-page.tsx`'s half does the same with `(id) => id`. The dnd-kit half
keeps its own `arrayMove`, untouched — it is the baseline. `bun run --filter playground build`
passes. While there, the same no-op `useMemo(() => ids, [ids])` the user caught in the README was
sitting in `comparison-page.tsx`; removed, and `SortableList` now takes `ids` directly.

**No CHANGELOG entry**, per the user (2026-08-12): the library has not been released, so 0.1.0 is
still being assembled rather than amended. Before release, that entry needs its subpath list
rebuilt — it says "Fourteen subpaths" and omits both `tree-drop-indicator` and `list`, so it is
**16** now.

`clamp` is duplicated from `tree.ts:215` rather than shared. Deliberate: it is a one-line numeric
primitive, and extracting it to a shared internal module would add exactly the cross-file hop
[T11.8](T11.8-readability-rewrite.md) existed to remove. Revisit only if a third copy appears.

Not done, and deliberately out of scope: **cross-list moves**. `applySortEnd` moves an item within
one array; the Backlog's kanban case needs a two-array signature and stays a Backlog item.
