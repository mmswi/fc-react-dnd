# T2.3 — `src/collision.ts`: `closestCenter`

**Phase** P2 — Core primitives · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

The one collision strategy this library ships (scope lock, [T0.5](T0.5-scope-lock.md)).
Public subpath `fc-react-dnd/collision`. Pure and directive-free so it stays
server-importable.

## Test first

Red tests before implementation:

- Picks the droppable whose centre is nearest the active rect's centre.
- Equidistant candidates resolve **deterministically by registration order**, not by
  object iteration order — assert the same input twice yields the same winner, and that
  reversing the candidate list does not flip a genuine winner.
- Empty candidate list returns nothing (not a crash, not a bogus id).
- A disabled droppable passed in **is** considered — filtering disabled entries is the
  caller's job, and a test should pin that boundary so nobody "fixes" it by adding a
  `disabled` check inside the math.

## Acceptance criteria

- Exports `closestCenter` implementing the `CollisionDetection` type from
  [T2.1](T2.1-public-types.md).
- No DOM access, no React, no `'use client'` — it operates on the rects it is handed.
- The disabled-droppable decision lives in the caller (the store's args), and the
  boundary is documented in a comment where a reader would otherwise be tempted.
- Exactly one strategy exported. Additional strategies are a Backlog item.

## Where it stands

`src/collision.ts` + tests on disk (2026-08-08); 8 tests green, subpath `./collision` added
to `package.json#exports`, `bun run verify` clean. Pure, directive-free, one exported
strategy.

The implementation is a single loop with a strict `<` comparison — that `<` rather than `<=`
*is* the deterministic tie-break, keeping the earlier candidate, which is registration order.
It is asserted in both list orders, plus a separate assertion that reversing the list does
**not** flip a genuine (non-tied) winner.

### The disabled-droppable boundary, and why the test is shaped the way it is

`DroppableCandidate` has no `disabled` field at all — the store removes disabled droppables
and measure-only rows before calling ([`ANALYSIS.md`](../ANALYSIS.md) § A9.6). So the test
pins the boundary from the other side: a candidate carrying `data: { disabled: true }` still
wins if it is nearest. That fails the day someone teaches the strategy to read policy out of
`data`, which would also break any custom strategy that uses `data` for something else.

### The red step caught a bad fixture, which is the point of running it

The "measures from centres, not overlap" case first failed because both fixture rects had
the *same* centre — it was passing/failing on the tie-break rather than on the behaviour it
claimed to test. Rewritten so the overlapping candidate's centre is 200px away and the
non-overlapping one's is 60px away, the case now discriminates a centre-distance strategy
from an intersection-based one.
