# T10.5 — The blog post

**Phase** P10 — Docs & the artifact · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

**This is the actual deliverable of the whole project.** The library is the evidence; this
post is the artifact. It explains how a drag-and-drop library keeps a 120 Hz pointer stream
from re-rendering React, and how to cross the line where every general-purpose library
stops: from the gesture (relative to one row) to the *position* — `(parentId, index, depth)`,
clamped, cycle-free (`ANALYSIS.md` § A2).

## How it gets written

- Load the **`explain-how-it-works`** skill first — this post is written in that style:
  concrete, jargon-demystified, following the actual data flow, so a reader can narrate it
  back afterwards.
- Follow one pointermove from DOM event to pixel. That path is the spine of the post.

## Acceptance criteria

The post covers, in a reader-can-follow-it order:

- **Store outside React** — why drag state lives in a plain external store created per
  provider, what `useSyncExternalStore` buys, and what breaks if the store is module-level
  (SSR, two providers).
- **Selector granularity** — why a component that reads `isOver` doesn't re-render when
  `transform` changes, with the render counts to prove it.
- **Rects measured once** — the layout-thrashing trap, why the move path does zero DOM
  reads, and how the dirty flag handles scroll without giving that up.
- **The tree math** — the heart of the post. Drop-into bands vs drop-between gaps, depth
  projected from pointer X, the `[next.depth, prev.depth + 1]` clamp and *why* that
  specific clamp, and cycle prevention by construction (excluding the active subtree in
  `flattenTree` rather than checking for cycles afterwards). **With diagrams** — this
  section is unreadable without them.
- **The numbers** — React Profiler render counts vs dnd-kit, from the actual run in
  [T9.6](T9.6-chrome-qa-and-profiler.md). State the scenario so a reader can reproduce it.
  **Estimated numbers are not permitted anywhere in this post**; if a number wasn't
  measured, it doesn't go in.
- Honest limits: what v0.1 doesn't do (one collision strategy, no cross-list moves, no drop
  animation) and why those were deliberate.

**The thesis, and the trap.** Build the post around the boundary established in
[`ANALYSIS.md`](../ANALYSIS.md) § A2: general-purpose libraries report *what gesture you
made relative to one row*; none returns the resulting *position*. The structural reason is
the good part — a per-drop-target hitbox physically cannot see the rows above and below, so
the depth clamp has nowhere to live. That is A1's root cause resurfacing, not an oversight.

Do **not** write that the ecosystem ignores trees. That was the project's original framing
and A2 proved it false: Atlassian's hitbox package ships `reorder-above` / `reorder-below` /
`make-child` / `reparent` / `instruction-blocked`. Credit it accurately — the argument is
about where everyone stops, not about neglect, and the precise claim is the stronger one.
Re-verify A2's findings before publishing; they were checked on 2026-08-07 and this
ecosystem moves.
