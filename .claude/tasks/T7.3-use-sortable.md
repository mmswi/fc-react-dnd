# T7.3 — `src/use-sortable.ts`

**Phase** P7 — Sortable list · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

The hook a list item uses: one node registered as **both** draggable and droppable, plus
the `translate` that moves it out of the way — read through a selector so an item only
re-renders when its own translate changes.

## Test first

Red tests before implementation:

- One element, two registrations (draggable + droppable), one ref — and both unregister on
  unmount, StrictMode-clean.
- `translate` comes from the memoized list projection ([T7.1](T7.1-list-projection.md)) via
  an O(1) selector; an item whose translate is unchanged by a move does **not** re-render.
- `isDragging` is true only for the active item.
- `handleProps` passes through from `useDraggable`, so a drag handle works exactly as it
  does on a bare draggable.
- Used outside a `SortableList`, it throws a named error rather than silently sorting nothing.

### The bug that took the longest to find, and the reason it hid

Memoising the projection buys **one computation per move**. It does not make the `Translate`
objects inside it stable — the projection itself is new each move, so its values are new
objects carrying identical numbers. Compared with `Object.is`, every item in the list
re-rendered on every pointermove: perf invariant 9 satisfied and perf invariant 4 quietly lost,
which is precisely the failure the render-count tests exist to catch.

Fixed by passing `translatesAreEqual` (new in `internal/geometry.ts`) as the selector's
comparison. Worth stating plainly because the two invariants look like the same claim and are
not: **memoisation controls compute, the equality function controls renders.**

A second lesson, from how long the diagnosis took: the fix was *written* early and silently did
nothing, because the patch text was matched against a pre-formatter version of the line and the
replacement no-op'd. The symptom — every item re-rendering — was identical before and after, so
it read as "the fix did not work" rather than "the fix is not there". Read the file, don't
assume the edit landed.

### `useSortable` exposes `isOver`

The result is `{ setNodeRef, handleProps, isDragging, isOver, translate }`. Composing
`useDroppable` already pays for the `isOver` subscription, so a row re-renders when it gains or
loses the drop target whether or not the consumer can read it — and a render spent on a slice
the consumer cannot see is a render spent on nothing. Exposing it makes the cost useful, and it
is what a sortable row usually wants for a drop indicator anyway.

The consequence for render counts is stated exactly rather than hidden: crossing one boundary
commits **three** rows, not two — the two whose translate changed plus the one handing `isOver`
to its neighbour. That is the number [T7.4](T7.4-sortable-granularity-tests.md) has to assert.

### A test-hygiene finding worth carrying forward

A `pointerSensor()` instance holds **one interaction at a time**, deliberately, so a second
finger cannot start a second drag. A module-level sensor shared across a test file means a test
that never releases the pointer blocks every test after it — four tests failed this way with
symptoms that looked like broken state. Each scene now builds its own sensor.
