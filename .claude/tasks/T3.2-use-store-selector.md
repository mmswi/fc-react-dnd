# T3.2 — `src/internal/use-store-selector.ts`

**Phase** P3 — Store & subscription layer · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

The one hook that connects React to the store, and the reason a 120 Hz pointer stream
re-renders almost nothing: components subscribe to a *slice*, and a store notification
that doesn't change their slice doesn't re-render them.

## Test first

Red tests before implementation:

- Selecting a slice that does not change across a notification renders the component
  **once**, not twice — assert on a render counter, which is the real claim.
- Selecting a slice that does change re-renders exactly once per change.
- The snapshot is cached. This is a **correctness** requirement, not a performance one:
  React calls `getSnapshot` again outside the render (the tearing consistency check —
  `ReactFiberWorkLoop.js:1617-1670`) and twice more on mount in DEV, which emits *"The
  result of getSnapshot should be cached to avoid an infinite loop"*
  (`ReactFiberHooks.js:1664-1674`). A selector returning a fresh object each call is an
  infinite loop, not a slow path. Assert reference stability directly. See
  [`ANALYSIS.md`](../ANALYSIS.md) § A3.2.
- **The selector runs on every notification even when nothing re-renders** — calling it is
  how React decides (`checkIfSnapshotChanged`, `ReactFiberHooks.js:1877-1886`). Assert this
  directly: notify the store N times with an unchanged slice, and check the selector ran N
  times while renders stayed at zero. That shape is the architecture's actual cost model
  ([`ANALYSIS.md`](../ANALYSIS.md) § A3.2), and a test that only counts renders will miss a
  selector that got expensive.
- A selector that **throws** forces a re-render rather than propagating into the store's
  notify loop (`:1883-1884`), so the error surfaces during render where a boundary catches
  it. Test it, and don't add defensive try/catch in the store for this case.
- The comparison reads the **latest** `getSnapshot` (`:1878`), not the one captured at
  subscribe time — so a component may change its selector between renders. Cover it.
- Store updates always schedule on **`SyncLane`** (`:1889`) and never receive transition
  priority. Don't document or design as if `startTransition` can deprioritize a drag.
- Custom equality is honoured (a structurally-equal new object does not re-render).
- Unsubscribes on unmount; StrictMode double-invocation leaves exactly one subscription
  (perf invariant 8).

## Acceptance criteria

- Built on `useSyncExternalStore` with a cached snapshot and an equality function.
- Re-renders only when the selected slice changes (perf invariant 4).
- No DOM access; no per-move allocation in the hot path.
- Typed generically over the selected slice — no `any`.

## Where it stands

`src/internal/use-store-selector.ts` + tests on disk (2026-08-08); 13 tests green,

### The bug the red run caught, and why it matters more than it looks

The first implementation cached `{ state, slice }` and short-circuited whenever the state
object was identical. That is wrong, and the "reads the latest selector" test failed on it: a
component that **changes its selector between renders** kept receiving the previous selector's
answer, because the state had not changed so the cache never re-ran anything.

The cache now keys on **both** the state object and the selector's identity:

```ts
cached.state === state && cached.select === select
```

Both halves earn their place. Consumers routinely pass an inline arrow, so `select` gets a new
identity on every render — which is exactly right: a parent re-render recomputes, while the
hot path (store notifications *between* renders, where `getSnapshot` is the same closure) still
short-circuits on the first comparison. This is the mechanism behind
`ReactFiberHooks.js:1878` reading the *latest* `getSnapshot` rather than the one captured at
subscribe time.

### `getSnapshot` is deliberately not memoised

It is recreated each render, closing over that render's `select`. A `useCallback` over a
latest-ref would leave one render reading the previous selector — the same bug in a different
place. `store.subscribe` is a stable method on the store factory, so React never resubscribes.

### Observed behaviour of a throwing selector

Confirmed rather than assumed: React catches the throw inside `checkIfSnapshotChanged`,
returns `true`, and forces a re-render, so the error surfaces **during render** where an error
boundary catches it. The store's notify loop is unaffected — the test asserts a listener
registered *after* the fragile component still fires. So no defensive `try`/`catch` belongs in
the store, exactly as the criteria say.

### The cost-model test is the one not to delete

`ANALYSIS.md` § A3.2's claim — the selector runs on every notification for every subscriber
whether or not anything renders — is asserted directly: 10 notifications with an unchanged
slice produce 0 body runs and ≥ 10 selector calls. A test that counted only renders would let
a selector that got expensive pass silently, and that is precisely how perf invariant 9 gets
broken.
