# T8.2 — `src/use-tree-drop.ts`

**Phase** P8 — Tree drag-and-drop (the flagship) · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Wire the pure tree math from [T8.1](T8.1-tree-math.md) to a live drag. `useTreeDrop` owns
the whole tree side of the React seam: it returns the live projection **and** wires rows via
`getRowProps(id)` (§ A7 D3 — one hook, no separate item hook, no way to hold it wrong).
Subscribers re-render **only when the projection changes** — not per pointermove. A tree
drop indicator that re-renders 120 times a second is exactly the thing this library is
arguing against.

**v0.1 tree mode is indicator-only**: rows do not translate live during a tree drag (that is
the sortable list's model). The projection drives one indicator. Live reflow in trees is a
Backlog item.

## Test first

Red tests before implementation:

- **Rows register measure-only** (§ A7 F7/D3): `getRowProps(id)` wires each row as a
  draggable **and** a measure-only rect registration — cached for projection and keyboard
  targeting, **excluded from collision**. Assert no `over` is ever produced by a tree row
  and that `closestCenter` receives zero tree-row candidates during a tree drag. Element
  hit-testing is the wrong question for trees (A1); it must not run against them.
- The projection is available during a drag and `null` outside one — and `null` when the
  active id is **not in this tree's `items`** (§ A7 F10: cross-tree guard; cross-tree moves
  are Backlog).
- **Granularity:** many pointermoves inside one gap re-render the consumer **zero** extra
  times; crossing into a different gap or switching between `into` and `between`
  re-renders **once**. Assert exact counts (perf invariant 4).
- **Memoization is two-level** (§ A7 F6): outer WeakMap on the per-provider store state
  object (the A5 two-provider collision safety), **inner WeakMap on the rows array
  identity** (staleness safety — the projection is a *function of* consumer rows, so a
  state-only key returns a stale projection after an auto-expand by construction). Mount
  several consumers and assert the compute count is 1 per (state, rows) pair; carry the
  two-provider regression test from [T7.1](T7.1-list-projection.md).
- **Rows not yet measured are excluded from candidates** (§ A7 F6): a row that mounted
  mid-drag participates only once the rect cache has it (the [T3.1](T3.1-store.md)
  structural path re-measures and mints a new state version). No crash, no guessed rect,
  at most one transient frame without it.
- **Every row selector must be a genuine O(1) read off the memoized projection.** The
  selector runs for every subscriber on every notification whether or not anything
  re-renders (A3.2), so one selector that recomputes makes the move path O(N²) and the frame
  is gone regardless of the render count. This is the most likely way to build something that
  passes every render-count assertion and still drops frames. See
  [`ANALYSIS.md`](../ANALYSIS.md) § A4.
- Keyboard depth: ArrowLeft/Right from [T5.2](T5.2-keyboard-sensor.md) produce a horizontal
  transform that lands in **the same** `projectTreeDrop` path as the pointer — assert the
  resulting projection, proving there is no parallel keyboard code path.
- **Keyboard reachability invariant** (§ A7 F9, accessibility invariant 1): every legal
  outcome — each gap at each legal depth, and 'into' on nestable rows — is reachable by
  keyboard alone. The test enumerates the legal targets for a fixture tree and drives arrow
  keys until each is visited. D1 makes this total ('into' is the deepest rung of the gap
  below the row); blocked gaps are skipped, not trapped in.
- A row that unmounts mid-drag cancels per the [A6](../ANALYSIS.md) policy (removal
  cancels); auto-expand mounting rows mid-drag does **not** cancel.

## Acceptance criteria

- Exports `useTreeDrop`; subpath `fc-react-dnd/use-tree-drop`.
- Returns the live `TreeDropProjection | null` plus `getRowProps(id)` (draggable wiring +
  measure-only registration + `aria` handle props passthrough). No public measure-only API
  on `useDroppable` — the registration kind stays internal.
- **`items` must be referentially stable across renders** — consumer contract, documented
  in the hook's TSDoc and README ([T10.1](T10.1-readme.md)): an inline `items` array (or
  inline `canNest`) recreates the rows identity every parent render and defeats the inner
  memo level, exactly the A4.3 footgun.
- **Announcements are projection-driven** (§ A7 F9): measure-only rows produce no `over`
  events, so tree drags announce on projection *changes* — "place inside X" / "place after
  X, level N" — with texts overridable via the `accessibility` prop like every other text
  ([T6.3](T6.3-accessibility-internals.md)).
- **Auto-expand recipe** (§ A7 F8), demonstrated in [T9.5](T9.5-playground-app.md) and
  documented in [T10.1](T10.1-readme.md): expand on hover *during* the drag (insertion —
  survives by design); restore collapse state only in `onDragEnd` / `onDragCancel` —
  restoring mid-drag unmounts rows, which is a removal, which **cancels the drag** per A6.
  That is the policy working, not a bug, and the recipe exists so consumers never hit it.
  The manual recipe is deliberate for v0.1 — a built-in `autoExpand: { delayMs }` helper
  that owns the timer and the restore bookkeeping is in the Backlog (user, 2026-08-08);
  don't ship it here ad hoc.
- Contains **no** tree logic of its own — every decision is delegated to `src/tree.ts`.
  If a rule is being re-implemented here, it belongs in [T8.1](T8.1-tree-math.md).
- No DOM reads during the move (rects come from the store's cache — perf invariant 1).
- `'use client'` at the top.

### Rows are measure-only, and it is asserted from collision's side

`getRowProps(id)` registers each row as a draggable **and** a measure-only rect. The test
substitutes a collision strategy that records how many candidates it was handed, and asserts
that number is **zero on every call** during a tree drag. Element hit-testing is the wrong
question for a tree (§ A1), so it does not run against tree rows at all rather than running and
being discarded.

### Row lifetime is owned by one effect, not by per-row ref cleanups

The obvious design — a ref callback that registers on attach and unregisters on cleanup — fails
immediately, and nine tests failed on it. `getRowProps` cannot call hooks, so the ref is all
there is; and a consumer's inline `ref={(node) => …}` wrapper is a new function every render, so
React detaches and re-attaches on **every** render, including the ones the drag itself causes. A
detach that unregistered would be a removal, which cancels the drag on its first move.

So: the ref **registers and never unregisters**, and `useTreeDrop` learns a row is gone the only
way it can — the consumer stopped asking for its props. Ids requested since the last commit are
collected during render and diffed in an effect. The set is only ever *added* to during render,
so a render React discards leaves a row registered one commit too long rather than unregistering
one that is still there. A second effect re-registers on setup and unregisters on cleanup, so
StrictMode's setup → cleanup → setup leaves every row registered rather than none.

The row-props builder lives **inside** the memo that holds the cache, so its dependency list is
the honest set of things baked into the closures it produces. (Biome's `useExhaustiveDependencies`
caught the earlier version, where the deps existed to invalidate a cache the factory never read.)

### Three real bugs the reachability invariant found

§ A7 F9 asks that every legal outcome be reachable by keyboard alone. Rewritten as the stronger
and more honest form — **every outcome the pointer can reach, the keyboard can reach** — it
found three defects, none of which any other test noticed:

1. **Vertical keyboard steps changed depth.** `findTargetInDirection` centres the item on its
   target, and in a tree the target's centre is offset by its indentation — so ArrowDown
   silently re-parented the item. Vertical steps now keep the horizontal position they had;
   depth stays the exclusive business of ArrowLeft/ArrowRight.
2. **The projection's vertical anchor cannot be the same for both sensors.** A pointer drag aims
   with the **cursor**. A keyboard drag has none, and stepping to a row's *centre* lands in that
   row's middle band every time — so `'into'` was the only mode a keyboard could ever produce
   and whole depths were unreachable. Keyboard drags now anchor on the dragged row's **leading
   edge**, which lands each step on a gap boundary; D1 is what makes that total, since `'into'`
   is the deepest rung of the gap below a nestable row.
3. **The cross-axis penalty punishes depth.** `findNearestRectInDirection` weights off-axis
   distance so ArrowDown prefers the item directly below. In a tree, deeper rows are further
   right *by design*, so that weight made ArrowUp prefer a shallow row three positions away over
   the deep row immediately above — and the rows it skipped were exactly the "first child of X"
   positions. The penalty is now an argument, defaulted for general layouts and **zero for
   vertical steps** in the store.

A fourth failure was the test's own: an unbalanced ladder (five ArrowRights, six ArrowLefts)
drifted the indent by a level per stop, so the deepest rung stopped being sampled a few stops
in. The ladder now returns to baseline exactly.

### Announcements

Tree rows produce no `over` events, so the live region would hear nothing between pickup and
drop. The store gained a small `announce` / `subscribeToAnnouncements` channel; `useTreeDrop`
pushes the projection through it from an effect, so it fires once per **committed** projection
change.

**Deviation from the criteria:** the text is overridden through `useTreeDrop`'s
`describeProjection` option, not through `DndProvider`'s `accessibility` prop. A projection is
not a provider-level concept, and threading it up would mean the provider — and every consumer's
`accessibility` object — knowing what a tree is. The tree hook is where someone configuring a
tree looks.

### Granularity

Asserted as exact counts: many pointermoves inside one gap re-render the consumer **zero** extra
times; crossing into a different gap re-renders **once**; switching between `into` and `between`
re-renders **once**. The projection is compared by value (`treeProjectionsAreEqual`), because the
memo yields a new object per move — the same lesson as [T7.3](T7.3-use-sortable.md), applied
before it could bite.
