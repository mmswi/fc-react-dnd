# T7.5 — `useSortable` returns `transition`; the drop commit never eases

## Goal

Kill the drop animation: a dropped row lands dead in its slot instead of painting offset and
gliding in. `useSortable` gains a `transition` result (`SORTABLE_SETTLE_TRANSITION` for a row
displaced by an active drag, `undefined` otherwise) so the decision lives in the library rather
than being re-derived — wrongly — by every consumer.

API addition, so its own task per the public-API policy. Opened by the user (2026-08-08):
"when I drop an element in this list, it comes from above into position … it should just drop
in position."

## The test that opens it

`src/use-sortable.test.tsx`:

```ts
it('is off for every row in the commit that ends the drag', () => {
  const list = renderList()
  dragBy(list.row('a'), ROW_HEIGHT_PX * 2 + 7)

  act(() => {
    fireEvent.pointerUp(document, { pointerId: 1, clientX: 0, clientY: ROW_HEIGHT_PX * 2 + 7 })
  })

  expect(list.transitionOf('a')).toBe('none')
  expect(list.transitionOf('b')).toBe('none')
})
```

## Acceptance criteria

- Displaced rows ease with `SORTABLE_SETTLE_TRANSITION`; the dragged row never eases.
- A row returning to its home slot **mid-drag** still eases.
- In the commit that ends the drag, no row eases.
- Untouched rows still never re-render on drag start or end.
- Both playground pages consume the returned `transition`.
- `bun run verify` green.

## Where it stands

Done. 471 tests, `verify` green. The revert check passes: substituting the demo's old rule
(`!isDragging → ease`) fails exactly the drop-commit test.

### The mechanism, because it will read as mysterious later

The drop commit does two things at once: the consumer's `onSortEnd` reorders the array (the row
jumps to its final DOM slot instantly) and the store reset zeroes every translate. Both land in
one commit — the pointerup handler is one task, React 19 batches it. A `transition: transform
200ms ease` still on the row in that commit animates the zeroing: a CSS transition starts from
the old computed value, so each moved row paints at `new slot + old translate` and glides to
`new slot`. For the dragged row the old translate is the full drag delta — dragged upward, it
paints *above* its slot and slides down, which is the reported symptom. Displaced rows do a
smaller version of the same wobble (their layout shift and transform reset cancel exactly, but
only after the 200ms glide).

The demo's `transition: isDragging ? 'none' : 'transform 200ms ease'` could not express the
fix: at the drop commit `isDragging` is already false, which is precisely when easing must be
off.

### Why the slice carries `isDragActive`, and why equality ignores it

Translate alone cannot distinguish the two zeroes: mid-drag, translate → 0 means "the row
glides home" (ease); at drop, the same 0 arrives with the reorder (never ease). The flag
answers it — but comparing it in the slice equality would re-render all N rows on every drag
start/end, exactly what the slice model exists to prevent. So `translateSlicesAreEqual`
compares translate only, and the flag rides along: it can go stale on a row whose translate
never changed, harmlessly, because a transition only matters in the commit where the transform
changes — and that commit re-renders the row with a fresh flag.

### Deliberate trade-off

A **cancelled** drag now snaps everything home instead of gliding back: the row-level state
transition is identical to a drop (`origin → null`), and telling them apart would need an
end-reason on the state. Backlog if it ever matters; a cancel that snaps is predictable, a drop
that glides was the bug.
