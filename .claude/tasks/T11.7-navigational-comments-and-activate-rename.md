# T11.7 — Make the call graph readable: backlinks at the seams, and one honest rename

**Phase** P11 — Defects found after v0.1 · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Two changes, both additive, both aimed at one complaint: you cannot follow how this code runs by
reading it.

1. **Navigational backlinks at every deferred-call seam** — where a closure is minted, name who
   invokes it; where it is invoked, name where it came from.
2. **Rename the colliding `activate` in `pointer-sensor.ts`** — one file, two functions, same
   name, unrelated jobs.

## Why

Raised by the user (2026-08-11), after three days reading the library:

> the main blocker when I read the code was that I was going all over the place and I couldn't
> see a clear link on why and how the code is used

Measured against the source, and the shape of the problem is specific:

| | |
| --- | --- |
| comment lines in `src/` | 1113 (31% of file bodies) |
| pointing **outward** — `ANALYSIS.md § A6`, `perf invariant 9`, `ReactFiberHooks.js:1859` | 57 |
| naming **another module in this library** | **1** |

So the comments are exhaustive about *why a line is the way it is* and silent about *where the
code goes next*. Rationale is only usable once you already know the flow; read first, it is a wall
of justification for decisions whose context the reader does not have yet. The navigational debt
every abstraction creates is never repaid.

**The concrete cost.** Answering "what happens when I press down" is 11 hops across 5 files, and
the chain is *re-entrant*:

```
use-draggable.ts:112  →  handle-props.ts:55   mints  beginDrag: (init) => store.beginDrag(id, init)
                      →  pointer-sensor.ts    (150 lines, activator → beginInteraction → threshold)
                      →  BACK INTO handle-props' closure     ← a file the reader already closed
                      →  store.ts:515         beginDrag
```

The reader has to hold a closure across a file boundary and re-enter a file they finished with.
The user pointed at `handle-props` as "too many abstractions" — the file itself is fine (two
callers: `useDraggable` and `useTreeDrop`'s `getRowProps`), but it is where the closure is minted
and nothing anywhere says who invokes it or when.

**The rename is an objective defect**, not a style preference:

- `pointer-sensor.ts:89` — `const activate = (pointer: Point)` → *starts the drag*
- `pointer-sensor.ts:237` — `activate: (context) => ({ onPointerDown })` → *returns event handlers*

Same word, same file, 148 lines apart, different jobs, different call times (threshold vs render).
`Sensor.activate` is public API (`types.ts:232`) and must not change; the **internal** one is free.

## The red test

Ground rule 2 wants a failing test first, and comments have no behaviour — but the backlinks do,
the moment they are allowed to rot. Open the task with a guard:

`src/internal/backlinks.test.ts` — scan every non-test file in `src/`, extract each
`<file>.ts:<line>` reference appearing in a comment, and assert the file exists and the line is in
range. Red first (there are zero such references today, so seed it with one real backlink and
watch it fail before the comment exists). This is the same mechanical check used on the
`coverage/explanations/` docs, moved into the suite so `bun run verify` protects it.

Optional second guard, decide while writing it: assert the referenced line still contains the
symbol the comment names, not just that the line exists. Stronger, and more brittle across
unrelated edits — probably worth it only for the ~12 seams, not for every citation.

## Scope — the seams to annotate

The deferred-call sites, from `grep`. Each needs a backlink at the definition **and** at the
invocation:

- `internal/handle-props.ts:55` — the `beginDrag` closure → invoked by `pointer-sensor.ts:93`
  (after the threshold) and `keyboard-sensor.ts:69` (on Space/Enter)
- `internal/store.ts:445` `subscribe` → receives React's `onStoreChange`, put there by
  `internal/use-store-selector.ts:76`
- `internal/store.ts:497` `addMonitor` → the five registrations in `dnd-provider.tsx`,
  `sortable-list.tsx:63`, `internal/live-region.tsx:66`
- `internal/store.ts:361` `createSession` → the object sensors hold for one interaction
- `internal/store.ts:194` `notify` / `:198` `emit` → who is in each Set, and that `emit` runs first
- `internal/auto-scroll.ts:185` `step` → polls the store, is not called by it
- `use-draggable.ts:78` / `:89` — the ref/effect split, pointing at the A6 cancel policy it exists
  to avoid tripping

## Acceptance criteria

- Every seam above carries a backlink naming the file and line on the other side of the hop.
- Backlinks are **additive** — no existing rationale comment is deleted or shortened to make room.
  Those encode the A6 policy and the ref/effect split, which cost real debugging to learn.
- `src/internal/backlinks.test.ts` fails before the first backlink exists and passes after; every
  referenced file:line resolves and is in range.
- The internal `activate` in `pointer-sensor.ts` is renamed to something that says what it does
  (`startDrag` / `promoteToDrag` — pick at implementation time). `Sensor.activate`, the public
  member, is untouched.
- No behaviour change: the full suite passes without any test being edited to accommodate the
  rename.
- `bun run verify` green.
- `mihai-coding-standards` closing checklist walked against the diff.

## Deliberately not in scope

**Flattening the re-entrant hop.** The chain would read linearly if the sensor received
`{ id, store }` and called `store.beginDrag(id, …)` at its own call site, instead of receiving a
pre-bound closure. That trades encapsulation for legibility — sensors would gain full store access
— and the sensor seam is locked public API, so it is a design decision for the user, not a
side-effect of a comment pass. Raise it again after this task lands and the remaining confusion
can be measured against a codebase that at least says where things go.

**Decomposing `store.ts`.** 413 lines, 29 methods, 6 shared mutable variables, so no method can be
read in isolation. Real, and a different-sized project. Noted here so it is not lost; it belongs in
Backlog or its own task, not bolted onto this one.
