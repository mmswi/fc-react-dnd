# T7.4 — Sortable render-granularity + StrictMode tests

**Phase** P7 — Sortable list · **Board** [`.claude/TASKS.md`](../TASKS.md) (status lives there)

## Goal

Prove the headline claim on the case the blog post leads with: dragging through a sortable
list re-renders only the items that actually moved. These are the numbers
[T10.5](T10.5-blog-post.md) quotes, so they must be asserted, not observed.

## Test first

This task *is* tests.

## Acceptance criteria

- With a list of N items (N large enough to be meaningful — 20+), crossing **one** item
  boundary re-renders only the items whose translate changed, asserted as an **exact
  count**. A range assertion would let a regression hide.
- Moving within a single item's bounds (many pointermoves, no boundary crossed) re-renders
  **nothing** — the strongest form of perf invariant 4.
- The whole flow runs clean inside `<StrictMode>`: no double registration, no leaked
  subscription, same render counts modulo StrictMode's deliberate double-render.
- Render counters are per-item, driven through real DOM events and the public API.
- The counts recorded here are cross-checked against the React Profiler numbers from
  [T9.6](T9.6-chrome-qa-and-profiler.md); a disagreement between the two is a finding, not
  a rounding difference.

## Where it stands

`src/sortable.granularity.test.tsx` on disk (2026-08-08); 6 tests green, `bun run verify`
clean. 24 rows, real DOM events, public API only.

### The numbers, stated exactly

Counted as **commits**, from a `useEffect` with no dependency array — unambiguous under both of
React's bailout paths, and directly comparable to [T9.6](T9.6-chrome-qa-and-profiler.md)'s
Profiler capture.

| Scenario (24 rows) | Commits |
| --- | --- |
| Crossing one row boundary | **3** — `row-0`, the row losing `isOver`, the row gaining it |
| 15 pointermoves inside one row | **0** |
| 10 consecutive boundary crossings | **30** — three per crossing, no drift |

The crossing case is asserted by **name**, not just count: `['row-0', 'row-5', 'row-6']`. The
other twenty-one rows have no changed slice and do not commit.

### It is three, not two, and the criteria's wording predates the reason

The criteria say "only the items whose translate changed". That is two rows. The third is the
row **handing `isOver` to its neighbour**, which [T7.3](T7.3-use-sortable.md) exposes
deliberately: composing `useDroppable` pays for that subscription whether or not the consumer
can read it, so the result surfaces it rather than spending a render on an invisible slice.
Three is the honest number and it is what the blog post must quote.

A final-state test complements the counts: after dragging row 0 over row 5, rows 1–5 carry
exactly `-40px`, row 0 carries `+200px`, and rows 6–23 carry nothing. That pins *what* changed
as well as *how many* things did.

### StrictMode

The same flow inside `<StrictMode>` produces the **identical** set of committed rows —
asserted by running both and comparing the sets, rather than by trusting that StrictMode only
doubles mount-time work.

## Amended 2026-08-08 — the dragged row now re-renders per move, deliberately

`useSortable` was giving the dragged row its projected landing slot, so it teleported between
slots instead of following the pointer. The user caught it in the demo. It now follows the
pointer, which costs **one component** one render per pointermove.

The table above still holds for every row that is *not* being dragged, which is the claim that
matters. The revised counts:

| Scenario (24 rows) | Commits |
| --- | --- |
| Crossing one row boundary | **3** — the dragged row, the row losing `isOver`, the row gaining it |
| 15 pointermoves inside one row | **15**, all of them the dragged row; the other 23 do not render |
| 10 consecutive crossings | **30** |

`trackTransform: false` restores the previous behaviour — 0 commits for moves inside one row — for
consumers whose `DragOverlay` carries the motion, and there is a test for both paths.

The lesson worth keeping: **a render-count test cannot tell you whether the result feels right.**
Every assertion here passed while the dragged row teleported. Counting renders is necessary and
not sufficient; someone has to drag the thing.
